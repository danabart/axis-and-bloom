# Flavor Intelligence Page — Part 2 of 2: Frontend (archetype grouping, lifecycle personalization, deeper content)

Depends on Part 1 (`CLAUDE_CODE_PROMPT_FLAVOR_INTELLIGENCE_PART1_BACKEND.md` in this folder) being live and tested: `GET /api/coffees/archetypes` (including its new `isDefault` field, Part 1 Decision #8), `GET /api/coffees/archetype-stats`, the extended `GET /api/coffees/:id/content` (now also returning `process`/`roastLevel`/`originRegion`, Part 1 Decision #7), the `?archetype=&slot=` deep-link contract, and the confirmed `GET /api/users/homepage-state` shape. Don't start this until that testing task is checked off.

## Context

Three problems, from Dana directly (2026-07-12): the sidebar is an unsorted wall of every coffee with no grouping; the page doesn't adapt to who's looking at it (new visitor vs. quiz-taker vs. repeat customer); and it should go deeper on the content it already half-shows (AI summary, dimension scoring, three-source notes) rather than staying a flat spec sheet. This file is the reorganization + personalization + depth pass. The content pipeline itself (AI summary, three-voice story, dimension bars, descriptor wheel) is not being rebuilt — see `WHAT_WE_BUILT.md` §"Our Coffees Page" — it's being reorganized and, in a few specific spots below, surfaced more fully than it is today.

File: `frontend/src/app/components/CoffeesPage.tsx`, renamed to `frontend/src/app/components/FlavorIntelligencePage.tsx` as part of this build (Part 1 Decision #5, reversed from an earlier draft — route and file both now change, confirmed with Dana). Supporting components in `frontend/src/app/components/coffee-info/` (unchanged, no rename needed there).

## Hard constraint — white-label / drop-ship confidentiality, absolute

Same rule as Part 1, restated because it's easy to violate accidentally on the frontend even when the API is clean: **roastery identity must never be visible to a customer anywhere on this page.** No `roaster`, no raw coffee `name`, no exact `origin` string — ever, not de-emphasized, not visible-if-you-look-hard.

**Revised same day**: `process` and `roast_level` are now shown directly (generic flavor vocabulary, not identifying), and `origin` is shown as a broad region only (`originRegion` from Part 1 Decision #7 — e.g. "East Africa," not "Sidama, Ethiopia"). Today's coffee header (`CoffeesPage.tsx`, the `selectedCoffee.roaster` / `.origin` / `.process` / `.roast_level` block) needs `roaster` and the raw `origin` string removed, but gets `process`/`roast_level`/`originRegion` back — see Decision #1 below. Don't pull any of these from a raw `coffees` row directly for "extra polish" — if it's not in the response shapes Part 1 defined (which already excludes `roaster` and raw `origin`), it doesn't belong on this page.

## Decisions

**Decision #1 — Sidebar becomes an archetype accordion, sourced entirely from `GET /api/coffees/archetypes`; coffee header drops roaster/raw name/exact origin but keeps process, roast level, and a broad origin region.**
Replace the flat `coffees` list/fetch in `CoffeesPage.tsx` with the Part 1 endpoint. One collapsible section per archetype (`archetypeLabel`, coffee count in the header), each containing cards for its active slots (`platformName`, position label from `positionLabel`). Drop `roaster`/raw name from every card — this endpoint never sends them, so there's nothing to accidentally render. Empty/`isActive: false` slots are omitted from cards entirely on this page (unlike The Bloom, which shows a "temporarily unavailable" placeholder because it's selling a fixed set of slots — this page is exploratory, so a slot with nothing in it yet isn't worth a card here).

The selected-coffee detail header loses `roaster` and the exact `origin` string, but keeps `process` and `roastLevel` as small tags (both now sourced from the extended `/:id/content` response, Part 1 Decision #7 — generic SCA vocabulary, not identifying). Add a new small "Origin" element showing `originRegion` (e.g. "East Africa") when set, `null`-safe (omit the element entirely for coffees with no region assigned yet, don't show an empty/placeholder state). **Presentation for `originRegion`, in increasing order of effort — pick based on how much time this deserves in one pass:** (a) a plain text badge/pill, consistent with the other tag pills, lowest effort; (b) a small labeled world-region icon next to the text; (c) a lightweight illustrative world outline with the relevant broad region highlighted — if built, follow The Axis page's existing precedent (`TheAxis.tsx`, hand-coded illustrative shapes, no real coordinates, no numeric precision, brand-color highlight fills) rather than a real map library/GeoJSON, since precision is exactly what's being deliberately avoided here. Recommend starting with (a) for this pass and treating (c) as a follow-up polish item, not a blocker — a text pill already fully satisfies "show origin at a high level, not exact," and a map is a nice-to-have on top of that, not a requirement of it.

**Decision #2 — Personalization covers every lifecycle stage explicitly, per the existing use-case taxonomy — not a coarse "has archetype or not" split.**
Per Dana directly (2026-07-12): this page should follow the same use cases already written and seeded in the DB, not a new invented bucketing. Those use cases are documented in full in `backend/src/features/customer_life_cycle/1_CLAUDE_CODE_PROMPT_CUSTOMER_STATE.md` (§"Use cases — what each stage should render") and already implemented once, for the homepage, in `Home.tsx`'s `renderStageCTA(stageCode, archetype, usualBlend, nextDeliveryDate)`. `user_lifecycle_stage` (Cloud SQL, 9 seeded rows, `code`/`label`/`description`/`sort_order`) is the authoritative list — this page's job is to render every one of those stages sensibly, the same way the homepage already does, not to reinvent the taxonomy. `GET /api/users/homepage-state` already returns everything needed (`stageCode`, `archetype`, `daysSinceQuiz`, `pendingFeedback`); no new backend work for this decision, only a frontend branch per stage, structured the same way `renderStageCTA` is (one function, one `if` per stage, easy to extend if a 10th stage is ever added).

This page is not the homepage, though — its job is exploration/education, not primarily conversion — so structure (which archetype section leads, whether "Your match" shows) stays simple and consistent across most stages, while the *secondary* nudge/copy varies more, mirroring what `renderStageCTA` does per stage but adapted to this page's purpose. Every case below still gets the full always-expandable accordion from Decision #1/#3 — personalization only changes what leads and what secondary copy appears, never what's accessible:

- **UC0 — Anonymous (no `user`).** Neutral accordion, no personalized header. Dismissible banner: *"Not sure where to start? Take the quiz to see your match →"* → `/find-my-flavor`.
- **UC2 — `NEW_NO_QUIZ`** (signed in, never quizzed). Same neutral accordion. Banner headline matches `Home.tsx`'s own copy for consistency: *"Ready to find your flavor?"* → `/find-my-flavor`. Can address the user by name if already cached from elsewhere on the page (no new fetch).
- **UC1 — quiz taken, never ordered**, three sub-stages exactly as `Home.tsx` buckets them by `daysSinceQuiz`:
  - `QUIZ_TAKEN_FRESH_NO_ORDER` (<30d) — "Your match: {archetype}" header, archetype section expanded first, adjacent archetypes "Worth exploring." No quiz mention (matches `Home.tsx`'s "no quiz mention" rule for fresh takers). Secondary link: *"Shop your match on The Bloom →"* (`/bloom`, not `/shop` — see note below).
  - `QUIZ_TAKEN_SETTLED_NO_ORDER` (30–180d) — same match-first layout; add a de-emphasized *"Retake the quiz →"* link, matching `Home.tsx`'s treatment.
  - `QUIZ_STALE_NO_ORDER` (>180d) — same match-first layout; secondary link copy changes to *"Palates change — retake anytime →"* (exact phrase reused from `Home.tsx` for consistency).
- **UC3 — pending feedback** (independent flag, not a stage — `homepage-state.pendingFeedback`, can coexist with any stage above per `2_CLAUDE_CODE_PROMPT_LIFECYCLE_FEEDBACK_FIX.md`). If present: a small secondary nudge near the match header, *"How was {pendingFeedback.blendName ?? 'your last coffee'}? Leave a quick note →"*, reusing the existing `OrderFeedbackForm` component `Home.tsx` already uses (`orderId`, `blendName`, `onSubmitted` props) rather than building a new one — same dismiss-and-suppress behavior (`localStorage` dismissal key), don't reinvent it. `blendName` here is `Home.tsx`'s existing field, already in production use for this exact purpose — not a new roaster-blindness concern since it's describing an order the user themselves already placed and knows the contents of, unlike Decision #2's `usualBlend` caution below (public-facing browse context vs. "your own order," genuinely different exposure).
- **UC4 — ordered before, not currently ordering**, four sub-stages exactly as `Home.tsx` buckets them:
  - `SUBSCRIBER` — match-first layout, but **no shop/reorder CTA at all** (they already have a standing order; a sales nudge here would be tone-deaf). Optional affirming line instead, e.g. *"This is the flavor intelligence behind your regular pick."*
  - `REORDER_DUE` — match-first layout, **no reorder CTA on this page** — that nudge already lives on the homepage (`Home.tsx`'s `REORDER_DUE` branch); duplicating it here is redundant/naggy across two surfaces. This page just shows their match, same as any other UC4 case.
  - `LAPSED_SINGLE_ORDER` — match-first layout, softer re-engagement framing echoing `Home.tsx`'s "New arrivals since your last order" spirit but adapted to this page's exploration purpose: lean the "Explore other flavor families" divider (Decision below) into slightly more prominent placement/copy for this stage specifically, e.g. *"It's been a while — here's what else is worth trying."* Nice-to-have copy variation, not a structural change; fine to ship without it if time-constrained.
  - `ACTIVE_REPEAT_USER` (and any unrecognized/future stage — same fallback principle as `Home.tsx`'s `renderStageCTA`) — match-first layout, no special nudge. Default case.

Within the UC1/UC4 match-first cases: the user's own archetype section renders first and starts expanded, adjacent archetypes (`useArchetypeAdjacency()`, already live data — see `useCompatibility.tsx`) render next labeled "Worth exploring" exactly as `CompatibilityBadge` already labels individual coffees, and the remaining archetypes render after that, collapsed, unlabeled. Every card everywhere still gets its per-coffee `CompatibilityBadge` exactly as it does today.

**Important, per Dana directly: this is about visual hierarchy, not access, for every stage above.** Every archetype section is always present, always expandable, and never hidden behind a login, a click-through, or a "see more" gate. Concretely: insert a plain divider row after the match + "worth exploring" sections, labeled *"Explore other flavor families"*, above the remaining collapsed sections — a visual cue that there's more, not a barrier to it. Don't paginate, don't truncate the archetype list, don't require an extra action beyond normal accordion expand.

**A note on "shop" links pointing to `/bloom`, not `/shop`:** `Home.tsx`'s existing CTAs still point to `/shop` — that's pre-existing staleness in a different page, out of scope here, not something to replicate. Per [[project_axis_bloom_ia]], `/bloom` is the current target browse+shop destination (`/shop` is being retired once Bloom absorbs it), so any new "go shop" link this build adds should point to `/bloom`.

**Do not use `homepage-state`'s `usualBlend` for browsing-context personalization on this page** (distinct from the UC3 `pendingFeedback.blendName` case above, which is safe — see that bullet). `usualBlend` resolves to `roaster_blend.blend_name`, and nothing in this codebase has confirmed that column is roaster-blind the way `coffee_alias.platform_name` is, in a context where the user is browsing the general catalogue rather than looking at their own specific past order. Archetype-based personalization already covers "what should a repeat customer see first" without touching this field. Worth a quick DB check outside this build if `usualBlend` is ever wanted for general browsing personalization; not blocking this one.

**Decision #3 — On the new `/flavor-intelligence` route, deep links read `?archetype=&slot=` (with a legacy `/coffees?coffee=` fallback); with no params at all, the default selection is lifecycle-derived, not "first coffee alphabetically."**
On mount:
1. If `?archetype=` and `?slot=` are both present, expand that archetype's section and scroll/highlight the matching card.
2. Else if the legacy `?coffee={id}` is present (old links, if any exist), call the Part 1 fallback resolution and replace the URL with the new param shape via `navigate(..., { replace: true })` rather than leaving the stale param in the address bar.
3. Else (the common case — a user just landing on the page directly, no referring link) — **the initial selection is derived from the same lifecycle signal as the rest of the page's personalization, not a hardcoded "first coffee in the list":**
   - Signed in with an archetype (any UC1/UC4 stage from Decision #2) → default to that archetype's section, expanded, with its `isDefault: true` slot (Part 1 Decision #8) pre-selected as the open detail panel. This is the natural continuation of "present their match first" — it's not just the top section, it's already open with the right card showing.
   - Guest, or signed in with no archetype (UC0/UC2) → default to the first archetype in the order `/archetypes` returns them, that archetype's `isDefault: true` slot, section expanded. This is a neutral pick, not a personalized one — no "Your match" framing applied to it, it's just today's implicit "something is open by default" behavior, now derived from the curated `isDefault` flag instead of alphabetical coffee name.

Today's page always has something selected by default (falls back to `data[0].id`, alphabetical) — this decision replaces that fallback with the `isDefault`-driven one above rather than removing the default-selection behavior entirely.

**Decision #4 — Compare mode picks a slot, not a raw coffee.**
Rebuild the compare dropdown from the already-loaded `/archetypes` data (`archetypeLabel` + `platformName` per option) instead of the old flat coffee list. Resolves to the same internal `coffeeId` for the three per-coffee fetches (`/content`, `/dimensions`, `/flavor-wheel`) exactly as today — only the picker's data source and displayed label change. This closes the one remaining identity leak Part 1 didn't already fix at the API layer (Part 1 Decision #6).

**Decision #5 — Descriptor wheel groups by SCA category instead of one flat bubble cloud.**
`v_collaborative_flavor_wheel` already returns `wheel_category`/`wheel_subcategory` per row, and `/api/coffees/:id/flavor-wheel` already passes them through — `CollaborativeFlavorWheel.tsx` just never grouped by them (`aggregateDescriptors()` flattens straight to a descriptor list). Change: group into labeled sub-sections by `wheel_category` (the 9 SCA Flavor Wheel top-level categories — e.g. "Fruity," "Sour/Fermented," "Green/Vegetative"), each rendering its own bubble cloud, sorted by total mentions within category. Keep the existing three-source color legend at the top (unchanged, already live data). This is the concrete version of "more SCA descriptor detail" — same underlying data, organized the way the SCA wheel itself is organized, instead of one undifferentiated cloud.

**Decision #6 — Surface cupper's free-text session notes; they're captured but currently dropped on the floor.**
`GET /api/coffees/:id/dimensions` already returns a `notes` array (`{ overall_notes, session_date }` per cupping session) alongside `dimensions` — but `CoffeesPage.tsx` only ever reads `dimData.dimensions` and discards `dimData.notes` entirely. This is exactly the kind of "notes being captured from a source but not shown" gap Dana flagged. Add a small collapsible "Cupping session notes" list (most recent first, `session_date` formatted, `overall_notes` as plain text) below the dimension bars — this is the cupper's own raw free-text, distinct from the AI-synthesized `three_voice_story`, and belongs to the "internal cupping" voice specifically. Omit the section entirely if `notes` is empty (most coffees will have this; don't show an empty state for what's effectively a bonus detail section).

**Decision #7 — New "Archetype intelligence" stats panel, one per archetype section, backed by `GET /api/coffees/archetype-stats`.**
Rendered once per expanded archetype section (fetch lazily on first expand, cache per archetype in component state — same pattern as the existing per-coffee content fetch). Shows each dimension's target range vs. `avgActual`, with `coffeeCount` framed honestly ("across 3 coffees cupped in this family" / "not enough cupping data yet" when `avgActual` is `null`). This is the family-level view; the existing per-coffee `DimensionBars` stays exactly as it is for the individual-coffee view — don't merge the two, they answer different questions ("how does this family typically taste" vs. "how does this specific coffee taste").

## Layout, top to bottom

1. **Feedback nudge** (UC3, `pendingFeedback` present only) — dismissible, above everything else, same pattern as `Home.tsx`'s `feedbackNudge`.
2. **Personalized header** (UC1/UC4 — signed in with an archetype) — "Your match: {Archetype}" + one-line description, same tone as `FlavorQuiz.tsx`'s returning-user panel, plus the stage-specific secondary line/link from Decision #2 (shop-your-match / retake-quiz / palates-change / subscription-affirming / re-engagement, as applicable).
3. **Quiz nudge banner** (UC0/UC2 — guest or no-archetype only) — dismissible, links to `/find-my-flavor`.
4. **Archetype accordion** — sections ordered per Decision #2 (match → worth exploring → "Explore other flavor families" divider → everything else, all always expandable, never gated); each section header shows `archetypeLabel` + coffee count; expanding a section reveals its cards (Decision #1) and, lazily, its stats panel (Decision #7). Initial expanded section + pre-selected card come from Decision #3's default-selection logic.
5. **Selected coffee detail panel** (opens by default per Decision #3, or on card click) — coffee header (`platformName` + `archetypeLabel`/`positionLabel` pills + `process`/`roastLevel` tags + `originRegion` badge, Decision #1) + compare toggle → compatibility badge/comparison text → surprise angle → three-voice story → collapsible AI note → **cupping session notes (new, Decision #6)** → dimension bars → descriptor wheel, now grouped by category (Decision #5).

2. Run the app locally (`npm run dev` in both `backend/` and `frontend/`) and actually click through every scenario in the Testing section above — every UC0–UC4 case, the deep-link cases, compare mode, the empty/sparse-data states — rather than reading the component code and inferring it must be correct.
