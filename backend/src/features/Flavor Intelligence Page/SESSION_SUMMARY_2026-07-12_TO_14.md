## Standing rules established this session

- **Heavy concurrent editing**: multiple other sessions (Dana directly, and/or Camila) were actively committing to this same repo throughout — Company Gift Subscriptions (B2B), a Bloom nav redesign, a Bloom `ArchetypeSection` refactor, Find My Flavor work, and QA scripts (`_qa_*.mjs`) all landed on `main` mid-session, sometimes multiple times per hour.
- **Never `git add -A` or `git add .` in this repo during a session like this.** Always `git add`/`git commit -- <exact paths>` limited to only the files this session actually intended to change. Run `git status --short` before every commit and read it — don't assume it only shows your own changes.
- **Never touch other sessions' in-progress planning docs** (`CLAUDE_CODE_PROMPT_B2B_*.md`, `CLAUDE_CODE_PROMPT_THE_BLOOM_PART10*.md`, etc.) even if `git status` shows them modified/untracked in your working tree — they're normal, expected, and not yours to stage.
- **Before every push**: `git fetch origin` then `git status` (or `git log --oneline main..origin/main`). If `origin/main` moved, `git merge origin/main` (not rebase — other commits are already shared/pushed history) and resolve conflicts by preserving both sides' intent, not by picking one side wholesale.
- **Always update `WHAT_WE_BUILT.md`** with a dated, numbered part entry per change (context, fix, verification — matching existing style). **Update `WHAT_WE_BUILT_DB.md` too** whenever a note there becomes stale (e.g. Part 6 changed what Part 4's DB note claimed) — don't just add new notes, re-read and correct old ones.
- Production **is** deployed continuously (GitHub Actions → Cloud Run + Firebase Hosting on every push to `main`) — the live backend API (`axis-bloom-backend-oiub7eumya-uc.a.run.app`) is directly queryable and was used repeatedly this session to verify fixes against real, current production state, not just local dev.

## Local testing pattern (Cloud SQL + Playwright)

See memory `axis-and-bloom-local-cloudsql-testing` for the full Auth Proxy setup (service account key BOM-stripping, port 5433, etc.). Additional things learned this session:
- The local backend's `express-rate-limit` (200 req/15min) **will** trip during a long verification session with many Playwright runs — if requests suddenly start failing/timing out, check `http://localhost:4000/health` first; a plain restart of the backend process clears the in-memory limiter instantly (faster than waiting).
- `GET /api/coffees/archetypes` is slow (multiple sequential per-slot DB round trips over the Auth Proxy tunnel, ~5–8s) — give Playwright generous timeouts (`waitForSelector(..., { timeout: 40000 })`), not the default.
- The newsletter modal (`NewsletterModal.tsx`) blocks clicks; dismiss via `[aria-label="Close modal"]` before interacting.
- No `chromium-cli` on this machine — used `npx playwright install chromium` from an isolated scratch `package.json` (installing it against the actual `frontend`/`backend` `package.json` gets refused by Playwright's CLI unless `playwright`/`@playwright/test` is already a listed dependency there).
- Always clean up afterward: stop the Auth Proxy, backend, and frontend dev server processes, delete the temp BOM-stripped service account key, delete scratch `.cjs` verification scripts from `backend/`/`frontend/` (never commit them).
