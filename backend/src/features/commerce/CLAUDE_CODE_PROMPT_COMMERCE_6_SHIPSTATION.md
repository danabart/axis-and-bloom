**The model (from Joe Bean's document).** Axis & Bloom owns a ShipStation account. Our backend creates each paid order there through the ShipStation API. An automation rule in our account assigns the order to Joe Bean as 3PL fulfillment provider and a carrier service; Joe Bean packs, prints the 4×6 label on **our** shared carrier account (we fund postage), and ships. ShipStation's ship-notify webhook tells us carrier, service, tracking and postage cost; that calls `shipmentService.markShipped`, which already records the shipment and emails the customer. Joe Coffee and any later roaster join by becoming a fulfillment provider in the same account with their own ship-from address and automation rule; our code routes per roaster.

**Decisions (Dana, 2026-11-18):**
1. Orders are pushed by our adapter through the API (not polled from a custom store).
2. Per line: item name = house name (the packing slip is customer-facing), SKU = the roaster's code from `coffee_sku.roaster_sku` (Joe Bean assigns its codes; we record them), roaster coffee name + roaster in the ShipStation internal notes. Packing slip template is Axis & Bloom branded, no roaster name, set in the Dashboard.
3. Postage is ours: our ShipStation carrier account, funded by auto-funding, shared with each provider. The service is chosen by the automation rule; we send a requested service from a parameter so the rule has a default to honour.
4. Routing is per roaster from day one: an order with lines from two roasters becomes two fulfillment requests, two ShipStation orders (`<orderNumber>-1`, `-2`), two shipments, two "on its way" emails. A roaster without ShipStation configured falls back to the manual email for its lines.
5. Customer sees: house names, Axis & Bloom packing slip, tracking link. Never a roaster name (same rule as everywhere).

## Part A — Schema (`schema.sql` additive, `comments.sql`, `catalog:md`)
Why nothing fits: `roaster` holds contact data, not an integration; `roastery_shipment_details` is the shipment fact and stays; `order_event` is per order, but placement is per order × roaster with retries and an external id, so it needs its own row and history; `stripe_event` is Stripe's ledger, ShipStation gets its own.
- **`fulfillment_adapter`** (lookup): `id`, `code UNIQUE` (`manual`, `shipstation`), `label`.
- **`roastery_fulfillment_config`**: `id SERIAL`, `roaster_id FK UNIQUE`, `adapter_code FK fulfillment_adapter`, `shipstation_tag TEXT`, `shipstation_ship_from_id TEXT` (ShipStation warehouse id, nullable), `requested_service_code TEXT` (nullable; falls back to the parameter), `is_active BOOLEAN`, `since`, `superseded_at` (supersede on change), `note`. Writer: `fulfillmentService.setRoasterConfigInTx`; admin page edits it.
- **`fulfillment_request`**: `id UUID`, `order_id FK`, `roaster_id FK`, `adapter_code FK`, `status FK fulfillment_request_status` (lookup: `pending`, `placed`, `failed`, `needs_attention`, `shipped`, `canceled`), `external_order_id TEXT` (ShipStation orderId), `external_order_key TEXT UNIQUE` (our idempotency key `ab:<order>:<roaster>`), `attempts INT`, `last_error TEXT`, `placed_at`, `created_at`. UNIQUE (order_id, roaster_id).
- **`fulfillment_event`** (insert-only history, same shape as `order_event`): `id`, `fulfillment_request_id FK`, `event_kind FK fulfillment_event_kind` (`created`, `placed`, `failed`, `needs_attention`, `provider_assigned`, `shipped`, `canceled`, `retried`), `note`, `source` (`finalizer | webhook | admin | cron`), `created_at`.
- **`shipstation_event`** (webhook ledger): `id`, `resource_url TEXT`, `resource_type TEXT`, `received_at`, `processed_at`, `error`, `payload JSONB`. UNIQUE on (`resource_url`, `received_at::date`) is not safe; use `payload->>'resource_url'` + a fetched shipment id for idempotency in code (shipments are idempotent on tracking number anyway).
- `shipping_carrier` add `shipstation_carrier_code TEXT` (mapping column; seed usps ↔ `stamps_com`, ups ↔ `ups_walleted`/`ups`, fedex ↔ `fedex`, dhl ↔ `dhl_express`; the webhook maps by this column, unknown → `other` + needs_attention note).
- `roastery_shipment_details` add `service_code TEXT`, `external_shipment_id TEXT`, `label_created_at TIMESTAMPTZ`, `fulfillment_request_id FK`.
- `commerce_parameter` seed: `shipstation_enabled` (0, Range 0–1), `shipstation_requested_service` (text, `usps_ground_advantage`), `packaging_weight_oz` (2, Range 0–16), `shipstation_push_retry_hours` (1, Range 1–24), `shipstation_needs_attention_after_attempts` (3, Range 1–10).
- Views: **`v_fulfillment_request_status`** (per request: current status, last event, external ids, shipment if any); extend `v_order_status` with `fulfillment_requests` count and an aggregate `fulfillment_status` that becomes `shipped` only when every request is shipped (`partially_shipped` as a new `order_fulfillment_status` code in between).

## Part B — Backend
- **`services/fulfillment/shipstation.ts`** (the adapter): `placeRequest(request)`: builds the ShipStation order: `orderNumber` = short order id + `-n`, `orderKey` = `external_order_key`, `orderDate` = paid_at, `orderStatus` = `awaiting_shipment`, `shipTo` from the order's snapshot (name from the profile), `billTo` = same, `items` = this roaster's lines (`sku` = `roaster_sku`, `name` = house name, `quantity`, `unitPrice` charged, `weight` = `weight_oz`), order `weight` = Σ line weights + `packaging_weight_oz`, `internalNotes` = roaster coffee names + roaster + our order id, `customField1` = our order id, `customField2` = roaster id, `tagIds` = the roaster's tag (created once through the API if missing, id cached in config), `requestedShippingService` from config or parameter. Idempotent: ShipStation upserts on `orderKey`. Rate-limited client with retry on 429. Logs through the structured logger.
- **`services/fulfillmentService.ts`** (one writer of `fulfillment_request`, `fulfillment_event`, `roastery_fulfillment_config`): `createRequestsForOrder(orderId)` groups lines by `coffee_sku.roaster_id`, one request per roaster, adapter from the roaster's active config (none → `manual`); `place(requestId)` calls the adapter, records `placed`/`failed`, bumps attempts, flips to `needs_attention` after the parameter; `markShippedFromWebhook(...)`; `retry(requestId)`; `cancel(requestId, reason)` (also deletes the ShipStation order when not yet shipped, recording the event; a refund-cancel path calls this).
- **`fulfillment/index.ts`**: `dispatchFulfillment(orderId)` becomes: create requests, place each; the manual adapter handles its requests as today (one email listing only its lines); order-level `fulfillment_status` derived (Part A view). The existing `order_event` kinds stay for order-level milestones.
- **Webhook `POST /api/webhooks/shipstation/:token`** (`routes/shipstationWebhook.ts`): token must equal `SHIPSTATION_WEBHOOK_TOKEN` (constant-time compare), else 404. Insert the ledger row, respond 200 fast, then process: fetch `resource_url` with the API, for each shipment find the request by `orderKey`/`customField1`, map carrier, call `shipmentService.markShipped(orderId, { carrier, trackingNumber, roasterId, shippedAt, serviceCode, postageCostCents, externalShipmentId })`, record `shipped` on the request, derive the order status. Unknown orders → ledger + no-op. Subscription: `fulfillmentService.ensureWebhookSubscription()` at boot when enabled (creates the `SHIP_NOTIFY` subscription once, stores its id in `commerce_parameter` text `shipstation_webhook_id`).
- **Cron**: a step in the daily job: retry `failed` requests older than `shipstation_push_retry_hours`; reconcile: for `placed` requests older than 7 days with no shipment, fetch the order from ShipStation and alert `admin_alert_email` (parameter `shipstation_stale_days`, 7).
- **Refunds**: Commerce 3's full-refund cancel now also cancels the roaster's request(s) when not shipped (ShipStation order deleted); if already shipped, the admin message says to contact the roaster, as today.
- **Admin**: `/admin/orders` drawer shows the requests per roaster (status, ShipStation link, Retry, Cancel); `/admin/roasteries` (or the existing roaster edit form) gets the fulfillment config fields; `/admin/commerce` shows the new parameters. Secrets: `SHIPSTATION_API_KEY`, `SHIPSTATION_API_SECRET`, `SHIPSTATION_WEBHOOK_TOKEN` in `deploy.yml`.
