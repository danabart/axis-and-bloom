# Coffee presentation, brief 1: the roaster's voice on every customer surface. Signature notes and an accent line (George Howell style), strength from evidence, the description written from the whole vault, awards without a name, admin aligned with what the customer sees. One topic value added, no new table.

> Folder: `backend/src/features/coffee_presentation/` · Written 2026-10-22 after Dana's review of Coado (Tiger Stripe, coffee 2914) on the Bloom page · Model: Opus for Part A (view logic with eleven readers) and Part D (prompts + guard), Sonnet for the rest
> Builds on: `cupping_evidence/DESIGN_CUPPING_EVIDENCE.md` v4 and brief 6 (customer voice). Everything there stands: insert-only evidence, roaster's words lead, our cupping adds confidence only, one writer per table, `*Reads` modules over views, nothing hard-coded, flags never gates.
> Status: done on prod 2026-10-23 (commit `c2f368b`, rev `axis-bloom-backend-00770-z88`; `CLOSING_REPORT_1.md`).

## Why (Dana, 2026-10-22)

Coado is one of the best coffees we have and its page reads badly. What she saw and what the code does:

1. **Eight notes at equal weight, five of them fruit, on a Chocolate & Nutty coffee.** All eight are the roaster's (Joe Bean's product page: Chocolate, Peanut Butter, Almond, Fig, Apple, Pear, Cherry, "fruit"; the portal form named the fruity family too). Nothing of ours reaches the page, that part works. What fails is the ranking: `CollaborativeFlavorWheel.tsx` orders by `mentions × intensity`, and brief 6 serves every row as `mentions 1, avg_intensity null`, so every note ties and the order falls back to the view's `display_order` (confirmed first, then alphabetical). Apple lands fourth. `SIGNATURE_COUNT = 5` is a literal in the frontend; the DB cap is 8. A family word ("Fruity") and a sub-group ("Dried Fruit", from Fig) render as notes beside leaves.
2. **The description is empty.** `three_voice_story`, `surprise_note` and `ai_summary` are null for 2914, so the reveal panel shows no prose. Either the daily `coffee-content-backfill` has not run since brief 6 shipped, or Haiku returned `INSUFFICIENT_DATA` and the `*_generation_failed` flag now blocks retries. Part F finds out. Beyond that, the prompts (`services/claude.ts getCoffeeSummary / getCoffeeSurpriseNote / getCoffeeThreeVoiceStory`) get only the descriptor words and the dimensions. The vault holds much more on this coffee that a customer should hear: the roaster's own sentences from the site (`roastery_remark` topics `general`, `brewing`, `roast`, `process`), the portal answers (`v_roastery_portal_current_response`: takes it black or with milk, brew notes, "anything else"), and the award ("Winner of a 2023 Golden Bean medal", today a `general` remark).
3. **Admin does not show what the customer sees.** `GET /api/admin/flavor-wheel/:coffeeId` reads `v_collaborative_flavor_wheel`'s roastery branch (accepted portal notes only) and never the website evidence, so the admin wheel and the Bloom page disagree on Coado by four notes. Dana: "we should align."

Reference for the look (Dana, 2026-10-22): George Howell Coffee. Under the coffee name, one line of three notes, comma separated, in dominance order ("Semi-Sweet Chocolate, Dark Cherry, Orange"); the prose carries the weighting in words ("a semi-sweet chocolate-cherry core with a hint of orange"); no bars, no wheel, no "show more".

## Decisions (Dana, 2026-10-22). Do not re-open.

1. **Nothing hard-coded in the frontend.** The page draws what the read returns, in the order it returns it. `SIGNATURE_COUNT` goes. Caps are `evidence_parameter` rows: `customer_voice_signature_max` (seeded **4**) and `customer_voice_accent_max` (seeded **3**). `customer_voice_max_words` is superseded (new row closing it, note: "replaced by signature/accent caps, coffee presentation brief 1"); nothing reads it afterwards.
2. **Signature vs accent, from a table that exists.** A customer-voice row is **signature** when its wheel family (tier-1 ancestor through `v_cupping_note_family`, never a `wheel_category` text match) is in `coffee_archetype.descriptor_families` of the coffee's match archetype (`v_coffee.match_archetype`); otherwise **accent**. A coffee with no match archetype has only signature rows. This is Dana's 2026-10-14 rule (a C&N blend with a fruity accent is plain C&N) made visible, and it follows the admin-editable families, so a change there changes the page.
3. **Strength from evidence, not from `mentions = 1`.** Per row: `n_roaster_channels` = distinct roaster channels naming the node (the accepted portal descriptor counts as `form`; `roastery_remark` rows naming the node count each distinct `channel`: website, cupping_table, email, call, visit, other; a bag note loads as a remark with its channel when that day comes); `roaster_rank` = the roaster's own rank on the current portal response (`roastery_portal_response_note.rank`) when the node is named there, else null; `cupping_share` = `cupping_sessions_named / cupping_sessions_total` when `confirmed_by_cupping`, else null. Order inside each group: `n_roaster_channels` desc, `roaster_rank` asc nulls last, `confirmed_by_cupping` desc, `descriptor`. Whether Cherry outranks Apple on Coado is then the data's answer (the form), and the closing report shows it before anything deploys.
4. **Tier rules.** A tier-1 node is never a note; it is only ever a family name. A tier-2 node (Dried Fruit, Berry) is a note only when the same coffee has no tier-3 row under it from any voice. Tier-3 rows always qualify.
5. **The look: one line, George Howell style.** Under the coffee name on the reveal panel: the signature notes as one comma-separated line in order ("Chocolate, Almond, Peanut"), capped by its parameter; beneath it, lighter and smaller, the accent clause built from data: "a hint of <family label lowercased>: <accent notes>" ("a hint of fruit: cherry, apple"), capped by its parameter, omitted when there are no accent rows; two or more accent families → one clause per family, in family order of first appearance. No bars, no category tags, no "show more"; the tail rows are not rendered anywhere on the customer side. `confirmed_by_cupping` stays available to the template for a small mark Camila may style later; not rendered by this brief. The dimension bars (`DimensionBars`) are untouched: they are A&B's instrument. The collapsed position card shows the same signature line in place of today's AI teaser when `surprise_note` is null, and keeps the teaser when it exists. The Flavor Intelligence page and the compare overlay (`variant='grouped'`, prelaunch-hidden) keep their grouped bars but read the same rows and the same order; their own literals, if any, move to the same parameters.
6. **One read for the roaster's voice on a coffee**, `roasterVoiceReads.getRoasterVoice(coffeeId)`, and every LLM surface reads it: the three content generators, the story (`generateCoffeeStoryWithRetry`), Liam's RAG (`sommelierRag`), the lifecycle email sentence (`routes/cron.ts` arrival note), the beats (`beatEngine`). Shape: `{ descriptors: CustomerDescriptor[] (with family, is_signature, n_roaster_channels, roaster_rank, cupping_share), remarks: { general: string[], brewing: string[], roast: string[], process: string[] } (current website / table / email remarks per topic, verbatim, latest capture per roaster × coffee as brief 6 C1 does for descriptors), portal: { takesIt, brewNotes, anythingElse, roastLevel, blendOrSingle, isDecaf, proposedArchetype } from v_roastery_portal_current_response or nulls, awards: { count: number } , dimensions: pooled rows as numericDimensionRows }`. Never in the shape: the roaster's name, `coffees.name`, `coffees.origin`, a remark of topic `origin`, or an award's text. No new table and no new view beyond Part A: `v_coffee_customer_descriptor`, `v_roastery_remark`, `v_roastery_portal_current_response` and `v_coffee_dimension_range` already hold every column; the read composes them (CLAUDE.md: say why no new object fits; this is why).
7. **Awards exist in the vault and never reach a customer by name.** `roastery_remark.topic` gains the value `award` (CHECK constraint widened; `comments.sql` updated). The existing Tiger Stripe `general` remark "Winner of a 2023 Golden Bean medal, this classic espresso blend" stays as it is (insert-only, nothing deleted); a new `award` row is inserted for 2914 with `remark = '2023 Golden Bean medal'`, `channel = 'website'`, `said_on` = the capture date of the general row, `record_source` naming that row's id and this brief, `recorded_by = 'coffee presentation brief 1'`. The write goes through the existing remark writer (`roasteryRemarkService` or whatever `comments.sql` names for `roastery_remark`), never inline SQL. Prompts receive `awards.count` only: "award-winning per the roaster: yes". The generated text may say "an award-winning blend, as the roaster tells it" and may not name the award, the body or the year. Dana, 2026-10-22: a googleable award sends the customer to the roaster; the roaster-blind rule covers awards.
8. **Attribution rules in every prompt that reads the roaster's voice.** The roaster's words lead. Flavor words are the wheel nodes only (`descriptors`), as brief 6 decided. Sentences from the site (`remarks`) are facts to paraphrase, never copied: at most the descriptor words appear verbatim. Every tasting claim is attributed ("the roaster calls it", "per the roaster", "the roaster recommends it with milk"); a confirmed word may add "and we tasted it too"; A&B never presents a tasting as its own. The signature / accent split shapes the sentence: the signature notes are the core, the accent is "a hint of". Roaster-blind as today: no roaster name, no raw coffee name, no origin beyond `originRegion`, no award name or year. When `descriptors` is empty the text is built from the dimensions and the portal answers alone; when those are empty too, `INSUFFICIENT_DATA` as today.
9. **Guard, config-driven, like `storyLayer.bannedTerms`.** After generation, the text is rejected and retried once when it contains the roaster's name, the raw coffee name (both already checked for the story), or any token of three or more characters from the coffee's `award` remarks (so "Golden", "Bean", "2023" each reject). The banned list is built per coffee from the data at generation time, never written into config or code. A second failure marks the field `*_generation_failed` as today and logs the reason.
10. **Admin aligned with the customer.** `GET /api/admin/flavor-wheel/:coffeeId`'s roastery branch reads `getCustomerDescriptors` rows (ranks 1 and 2) instead of the wheel's roastery branch, each tagged `form` / `website` / both by `n_roaster_channels` detail; the internal branch (consensus) and the client branch are unchanged. `AdminFlavorWheel.tsx` gets a block at the top, **What the customer sees**: the signature line, the accent clause and the three stored texts exactly as `GET /api/coffees/:id/content` would serve them, plus a `Regenerate` button that calls the existing `POST /api/admin/coffees/:id/refresh-content`. The workbench Descriptors tab's "Who named it" table gains a `customer sees` column (signature / accent / hidden by cap / hidden by tier).
11. **Regenerate everything active**, after the prompts change, through the existing backfill, after clearing the three `*_generation_failed` flags on active coffees (one `UPDATE` through the content writer `comments.sql` names for those columns; not the story flag, Dana edits stories by hand). The closing report prints the three texts for 2914, 2917, 2905 and 2934 and says, for 2914, why the fields were null before this brief (flag set, or never generated).
12. **No new table. One `ALTER` (the topic CHECK). Nothing deleted, no catalog write, no signal, no merge.** Prod only after Dana's go on the test closing report.
