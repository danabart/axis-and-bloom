## Why (Dana, 2026-10-21)

The Balance cupping (session 40) showed two things:

1. **One session drove everything.** Four coffees cupped on one table all read lower on acidity than in September, and the ranges, the band check and the dial signal all followed that one table. A range is evidence from every time we cupped the coffee, with recent cuppings counting more; one session is a sample, not the answer.
2. **Cupping notes pile up, and the pile leaks outside.** Internally, insert-only is right. But the admin pages list every merged row's descriptors as rows, so twenty cuppings of Union will show twenty rows of cocoa; and the customer story (`routes/coffees.ts fetchCoffeeDataForContent`) takes the top 8 descriptors by mention count across all sources, so the more we cup the more the customer hears us and the less they hear the roaster. The roaster's website words never reach the customer at all (they live in `roastery_remark`, not in the wheel). Dana's rule: **the roaster's notes lead. Ours appear outside only on a hit.**

## Decisions (Dana, 2026-10-21). Do not re-open.

1. **Pooled range, weighted by rank and by time.** Per coffee × dimension, every current merged row (every session) contributes its converted range. Each session's weight has two factors, multiplied, then normalised over the coffee's sessions:
   - **Rank weight** (Dana: "two sessions: 40/60; make it sensible for more"): sessions ordered latest first, rank 0, 1, 2, …; `rank_weight = param('session_rank_ratio') ^ rank`, ratio seeded **0.667**. Two sessions → 60 / 40; three → 47 / 32 / 21; four → 41 / 27 / 18 / 12; one → 100. One parameter reproduces the 40/60 and extends to any n.
   - **Time weight**: `0.5 ^ (days between that session and the coffee's latest session / param('session_half_life_days'))`, half-life seeded **365**. Two sessions three weeks apart are barely touched by it; a session a year older than the latest counts half again as much less.
   Pooled min / max / midpoint are the weight-normalised averages of the sessions' min / max / midpoint. Both parameters are **editable from the admin portal** (Part E) and the Dimensions tab shows the weight each session received, so a change is visible the moment it is made.
2. **Sessions can disagree.** When any two pooled sessions' midpoints differ by more than `param('session_gap')` (seeded **2**, same unit as `cupper_gap`), the dimension carries `sessions_disagree = true`. It is a flag, never a gate; it joins the existing flag set (`cuppers_disagree`, `roaster_disagrees`, `both`, `one_source`) in `v_evidence_dimension` and on the workbench Dimensions tab. The history view stays as it is; it is where you see which session pulled.
3. **The same view, the same name.** `v_coffee_dimension_range` keeps its name and every existing column, so its nine readers (cuppingReads, roasteryPortalReads, customerIntegrity, `v_archetype_dimension_comparison`, `v_coffee_dimension_range_calibrated`, `v_palate_shared_traits`, and the three more `comments.sql` lists) inherit the new semantics without being touched. `session_id` / `session_date` keep meaning **the latest session** (that is what `evidence_newer_than_decision` and `placed_from_session_id` compare against). New columns are added, never renamed: `n_sessions_pooled`, `weight_latest_share` (the latest session's share of the total weight, 0 to 1), `session_weights` (JSON array of `{session_id, session_date, weight}` ordered latest first), `sessions_disagree`, `rank_ratio`, `half_life_days`. `n_scores` becomes the count of cupper rows behind every pooled session; `all_ab_scale` is true only when every pooled session is all `ab_0_15` (the dial signal still fires only on true). The unmerged fallback (a coffee with cupper rows but no merged row) is unchanged.
4. **The dial signal reads the pooled midpoint** through the same `cuppingReads` call it reads today; nothing in `dialSuggestion` changes except the `notes` text, which now says `pooled n sessions (ratio <r>, half-life <d> d), latest s<id>`. No signal is re-recorded by this brief: the next merge or `refreshDialSignal` on a coffee picks the new basis up. The closing report shows, for the 22 cupped coffees, the old midpoint, the new pooled midpoint and whether the suggested slot would change, **without recording anything**.
5. **Admin: descriptors are a consensus, not a list.** New view `v_evidence_descriptor_consensus`: one row per coffee × SCA node (at the tier the cuppers used, from the current **cupper** rows, not the merged rows): `sessions_named`, `sessions_total` (sessions in which that coffee was cupped by anyone), `share = sessions_named / sessions_total`, `cuppers` (array of cupper names, from `cupper`), `first_named`, `last_named`, `words` (distinct `custom_notes`). The admin Flavor Wheel's internal branch and the workbench Descriptors tab read this view and show `cocoa · 2 of 2 sessions · Dana, Camila` instead of rows. `v_collaborative_flavor_wheel` itself is not changed (its internal branch is observation-level and other admin readers depend on it).
6. **Outside: the customer voice.** The roaster's words, **as flavor-wheel nodes only**, are what the customer hears: the `descriptor` column is always `cupping_note.descriptor`, never the roaster's raw text, and a roaster note with no node (`cupping_note_id` null, e.g. "graham cracker") is not in this view at all (Dana, 2026-10-21: "customer should see terminology only from the flavor wheel"). Our cupping never adds a word outside; it adds **confidence** when it agrees. New view `v_coffee_customer_descriptor`, one row per coffee × node the customer may hear, with `voice` and `rank`:
   - rank 1 `roaster_accepted`: `roastery_coffee_descriptors` where `is_active` (what Dana accepted from the portal).
   - rank 2 `roaster_website`: `roastery_remark` with `channel = 'website'`, `topic = 'descriptor'`, a node resolved per C0 (stored or through the current mapping), not superseded, from the **latest capture** per roaster × coffee (same latest-capture rule brief 3 used). Mapping a word in the admin portal therefore changes what the customer hears the next time the page loads; that is the decomposition work Dana already does, applied outside.
   - rank 3 `customer`: `customer_feedback_descriptor` through `customer_feedback_event`, as the wheel has it today (the third voice; it grows into the collaborative wheel).
   - **No row from our cupping.** A node we named that the roaster did not name stays inside (Dana: "most likely we are off").
   - **Hit = confidence.** A roaster row (rank 1 or 2) carries `confirmed_by_cupping = true` when `v_evidence_descriptor_consensus` for that coffee has a node that is the same node, a descendant of it, or an ancestor of it (walk `cupping_note.parent_id` both ways: roaster "Citrus Fruit" and we "Tangerine" is a hit; roaster "Orange" and we "Citrus Fruit" is a hit), provided the shared node's tier is ≥ `param('customer_voice_hit_tier')` (seeded **2**): both saying only "Fruity" is not a hit. The row also carries `cupping_sessions_named` / `cupping_sessions_total` from the consensus row that confirmed it, so the story can say how often we tasted it. The same shape is ready for `confirmed_by_customers` later (not built now).
   - One row per node (the lowest rank wins); `display_order` = rank, then `confirmed_by_cupping` desc. No cap in the view; the cap is `param('customer_voice_max_words')` (seeded **8**) applied by the read.
7. **Readers of the wheel are sorted into two piles.** Every reader of `v_collaborative_flavor_wheel` (`comments.sql` lists them: `v_coffee_descriptor`, routes/coffees.ts, routes/orders.ts, routes/cron.ts, routes/admin.ts, beatEngine, catalogService, evidenceReads, sommelierRag, and whatever else `grep` finds) is classified in the closing report as **customer-facing** (a customer, Liam, a beat, an order page or email can see the words) or **internal** (an admin page or a check). Customer-facing readers switch to `v_coffee_customer_descriptor` through one new read, `cuppingReads.getCustomerDescriptors(coffeeId)` (cap applied, `display_order`); internal readers stay. `routes/coffees.ts` loses its inline SQL and calls the read. The customer story's voices become roaster (ranks 1 and 2, with `confirmed_by_cupping` available to the template so it may say the roaster's word is one we tasted too) and customers; there is no internal-words voice any more. When there are no roaster words, the story has dimensions and archetype and no descriptor sentence. `v_coffee_descriptor` (read by `v_palate_shared_traits`, cuppingReads): report who reads those and whether a customer sees the result; if yes, they switch too; if unsure, STOP and report before changing them.
8. **The dimensions a customer sees** come from `v_coffee_dimension_range` as before, which after Part A means the pooled range. Nothing to do beyond Part A; name it in the report.
9. **Workbench Dimensions tab.** Per-cupper cells show the session tag of the row they come from (today Dana's Body on Fabricator reads `5–7` from s37 next to a merged `6 · s40`, which misleads); the merged column header says `pooled · n sessions`; a `sessions disagree` pill appears in the Flag column; the row's history (per session) opens from the cell, reusing `v_coffee_dimension_history` which `cuppingReads` already serves.
10. **Parameters, not literals, and editable.** Five new `evidence_parameter` rows (`session_rank_ratio` 0.667, `session_half_life_days` 365, `session_gap` 2, `customer_voice_hit_tier` 2, `customer_voice_max_words` 8), each with a note, read through `param()` in the views and through `evidenceReads`/`cuppingReads` in code. No number from this brief appears in a view body or a `.ts` file. Dana edits them from the admin portal (Part E): a change is a new row that supersedes the current one (the table already has `since` / `superseded_at` and the partial unique index), never an UPDATE.
11. **No table changes, no catalog writes, no re-merge, no signal recorded, nothing deleted.** Flags never gates. Prod only after Dana's go on the test closing report.

## PART A: pooled range
A1. Rewrite `v_coffee_dimension_range` per decisions 1 to 3. Suggested shape: `history AS (SELECT … FROM v_coffee_dimension_history)` is **not** reused (it would make the range depend on a view that depends on nothing else; fine) — either way, the pooled CTE computes per coffee × dimension: `latest_date = max(session_date)`, `rank = dense_rank() over (partition by coffee_id, dimension_id order by session_date desc, session_id desc) - 1`, `w = power(param('session_rank_ratio'), rank) * power(0.5, (latest_date - session_date) / param('session_half_life_days'))`, `value_min = sum(w*min)/sum(w)`, `value_max = sum(w*max)/sum(w)`, `midpoint = round((value_min+value_max)/2, 2)`, `n_sessions_pooled = count(distinct session_id)`, `weight_latest_share = sum(w) filter (where session_date = latest_date) / sum(w)`, `sessions_disagree = max(midpoint) - min(midpoint) > param('session_gap')`, `session_weights = json_agg({session_id, session_date, weight: w/sum(w)} order by session_date desc)`, `rank_ratio`, `half_life_days`. A coffee cupped twice in one session (two session coffees, e.g. a control) shares that session's rank and weight between its rows. Keep `basis`, `session_id`, `session_date` (latest), `n_scores`, `n_sessions`, `all_ab_scale` as decision 3 says.
A2. `v_evidence_dimension`: add `sessions_disagree` and extend `flag` with the value `sessions_disagree` (combinations: keep the existing scheme; if `flag` is a single text, add the new value and let `both` keep meaning cuppers + roaster; the tab shows pills, one per true flag, so prefer exposing booleans and let the tab render).
A3. `v_coffee_dimension_range_calibrated`: it reads "latest session" cupper rows; leave it pooled-unaware but make it read the latest session from the new `session_id` column (no behaviour change) and say in its comment that it is latest-session by design until Dana decides on offsets.
A4. `comments.sql`: update the Purpose of `v_coffee_dimension_range`, `v_coffee_dimension_history` ("the catalog reads the pooled range"), `v_evidence_dimension`; add the new views of Parts B and C with Writer: none (derived) and full Readers lists. Regenerate `CATALOG.md`.
A5. `DESIGN_CUPPING_EVIDENCE.md`: a v4 note at the top and in §7 replacing the latest-session rule with decisions 1 to 3; `README.md` in the folder: status line.
