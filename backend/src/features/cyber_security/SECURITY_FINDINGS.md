## Verified SAFE (checked because it looked risky — no action)
- **SQL injection:** none. Every query is `$n`-parameterized; the one dynamic `SET` clause joins only hardcoded column names.
- **IDOR:** users, orders (`WHERE o.id=$1 AND up.firebase_uid=$2`), addresses, households (invite needs a 32-byte token + email match), QR (16-byte token + ownership check) all scope to the caller.
- **Admin API:** `router.use(requireAdmin)` on every admin router, with a Postgres `user_type='admin'` check — server-enforced, not just hidden UI.
- **LLM markers:** `remember` / `card:adjust` / `open_dial` / `save_recipe` are all whitelist-verified server-side and scoped to the caller's own uid — a forged id can only touch the attacker's own data. No cross-user effect.
- **LLM output:** `max_tokens` bounded on all 6 model call sites; output stored and rendered as escaped React text; no `dangerouslySetInnerHTML` anywhere. No stored XSS.
- **Secrets/bundle:** no Anthropic/Shopify-admin/Resend/service-account/CRON secret in the frontend or any `VITE_` var (only the public Firebase web config); no `.js.map` shipped.
- **CI triggers:** `push: main` only — no `pull_request_target`, no untrusted-PR code running with secrets. Secrets injected via GCP Secret Manager `--set-secrets`, not baked into images. `.env` / key files gitignored. `reporting_ro` DB role is NOLOGIN, view-only.
- **Cron:** all jobs behind `requireCronSecret`, which fails closed if the secret is unset.
- **Password reset:** enumeration-safe (returns ok regardless of whether the email exists).

## Live production scan — 2026-08-05 (axis-and-bloom-prod.web.app)
Confirmed against the running site (browser network trace + same-origin header probe):
- **M5 confirmed live.** The static site (Firebase Hosting) returns **zero** security headers — no HSTS, X-Content-Type-Options, X-Frame-Options, CSP, Referrer-Policy, or Permissions-Policy. The pages your users load are unprotected. → C12.
- **API is well-defended (good).** `/api/*` (Cloud Run + helmet) returns HSTS, X-Content-Type-Options, X-Frame-Options, CSP, and Referrer-Policy; `x-powered-by` is hidden. Only `Permissions-Policy` is missing. So protection currently **stops at the API boundary** — the site itself is the gap.
- **M10 confirmed live.** An anonymous Firebase identity is minted on every page load (`identitytoolkit …/accounts:lookup` fires unauthenticated on first paint). → C6 + C16.
- **M2 confirmed live.** The coffees page calls the public `GET /api/coffees/:id/content` on load — the on-demand AI-generation path is a real, reachable surface. → C3.
- **No source maps** are loaded by the production bundle (consistent with the earlier static-bundle finding).
- **M1 nuance:** `/health/db` is mounted at the Cloud Run root, and Hosting only rewrites `/api/**`, so it is **not** reachable through the public `web.app` domain (that path serves the SPA). The schema leak is exposed only at the **direct Cloud Run origin** — still worth removing (C1), but lower real-world reach than if it were on the main domain. **Removed 2026-08-07 — see Fixes applied below.**

## Fixes applied — 2026-08-07
- **M1 (schema-leak diagnostics) closed.** Deleted `GET /health/db` and `GET /health/session-cols` from `backend/src/index.ts` — both unauthenticated, both handed an attacker a free data-model map (all public-schema table names; `cupping_sessions`' column names/types). `GET /health` untouched (still `{ status: 'ok' }`, no auth — Cloud Run/uptime checks depend on it and it exposes nothing). Verified live against the actual Cloud Run origin (the only place these were ever reachable, per the M1 nuance above): `/health` → 200, `/health/db` → 404, `/health/session-cols` → 404. Full detail: `WHAT_WE_BUILT_SECURITY.md` entry 2.
- **M11 (rate limiting) closed.** Confirmed empirically (temp logging route, real Cloud Run log reads, not assumed) that X-Forwarded-For never carries the real visitor IP through Cloudflare -> Firebase Hosting -> Cloud Run — Firebase Hosting's rewrite replaces it with its own 2-entry chain. CF-Connecting-IP does carry the real IP but is spoofable on both the `*.web.app` and `*.run.app` direct-origin paths (also confirmed by direct test). New `backend/src/middleware/clientIp.ts` trusts CF-Connecting-IP only when X-Forwarded-For's second-to-last entry is a published Cloudflare IP; otherwise falls back to `req.ip` (trust proxy=1, non-spoofable). Wired into every `express-rate-limit` instance. Full detail: `WHAT_WE_BUILT_SECURITY.md` entry 1. One known residual gap documented in the code and there too — a direct `*.run.app` hit that forges a real Cloudflare IP into X-Forwarded-For can still spoof the keyed IP. **Not closable by restricting Cloud Run ingress** (confirmed 2026-08-06: Firebase Hosting's `/api/**` rewrite requires ingress = "All," so restricting it breaks the whole API) — closed instead once **C6** (Firebase App Check) is enforced, which rejects a direct-origin request with no valid App Check token before it reaches the limiter. C6 must exempt the `requireCronSecret` routes (`/api/cron/*`, `/api/webhooks/*`), which legitimately call `*.run.app` directly. **2026-08-09 follow-up:** the global backstop's default (200/15min) proved too tight for real multi-user traffic (a shared IP like mobile CGNAT can legitimately carry many customers at once) — raised to 2000 and made env-configurable (`GLOBAL_RATE_LIMIT_MAX`/`GLOBAL_RATE_LIMIT_WINDOW_MS`); per-route abuse guards unchanged. See `WHAT_WE_BUILT_SECURITY.md` entry 6.

**2026-08-08 follow-up:** C6 (Firebase App Check) is deployed in monitoring mode (see H2 above and `WHAT_WE_BUILT_SECURITY.md` entry 7) — the residual gap this entry documents is not yet closed, since nothing is enforced. It closes once `APP_CHECK_ENFORCED` flips to `true`.

**2026-08-09 follow-up: closed.** `APP_CHECK_ENFORCED=true` shipped (C6-enforce Stage 1, `WHAT_WE_BUILT_SECURITY.md` entry 9). A direct `*.run.app` request with no valid App Check token — including one that forges a Cloudflare IP into `X-Forwarded-For` — now gets `401` before it ever reaches the rate limiter, live-verified with a genuine minted token (200) vs. no token (401 `app_check_failed`).

- **H3 (beats dial-in IDOR) closed.** `GET /api/beats/dial-in/:beatEventId/respond` identified the beat by `beat_event.id`, a plain SERIAL — unauthenticated, no ownership check, trivially enumerable. Replaced with a capability token (`respond_token`, 32 random bytes via `crypto.randomBytes`, hex-encoded, unique), the same pattern already used for `household_invitation.token` and `coffees.qr_token`. The route now looks up `beat_event WHERE respond_token = $1 AND beat_type = 'dial_in'`; no match → `404`, no distinguishing signal between "wrong token" and "no such beat." The SERIAL id no longer appears in any respond URL. Applied via a proper 3-step ordered migration (nullable column + unique index → app-side backfill via `crypto.randomBytes`, since this DB has no `pgcrypto` extension for SQL-side random bytes → `SET NOT NULL`), run directly against production **before** the new code deployed; `beat_event` had zero rows at the time (pre-launch — no dial-in beat has ever been sent), confirmed empirically, so no outstanding old-format link exists to break. All 6 `INSERT INTO beat_event` sites (`beatEngine.ts`) now generate a token at row-creation. `expectation`'s whitelist validation (`lighter`/`as_expected`/`bolder`) was already present and is untouched. Full detail: `WHAT_WE_BUILT_SECURITY.md` entry 5.
- **M2 (public coffee AI endpoints generating on cache-miss) closed.** `GET /api/coffees/:id/content` and `/:id/ai-summary` are now pure reads — the inline `generateAndStoreAllContent`/`generateAndStoreSummary` calls are gone entirely from both public handlers; a cache-miss returns `200` with null/empty fields (the frontend already renders that state gracefully — `TastingNotes.tsx`'s "Not enough data to generate a summary yet." — no frontend change needed), never a generation attempt, never a `500`. Generation moved fully out-of-band: a new daily cron job, `GET /api/cron/coffee-content-backfill` (`requireCronSecret`, same shape as the three existing daily jobs), finds coffees still missing content and generates for them sequentially — chosen over an admin-only trigger because it keeps the cache populated automatically as new coffees are added, without relying on a human remembering to click refresh; the existing admin `refresh-content`/`refresh-summary` endpoints (`requireAdmin`, already non-public, untouched) remain as the manual force-regenerate path. New terminal-failure flags (`ai_summary_generation_failed`/`surprise_note_generation_failed`/`three_voice_story_generation_failed`/`story_generation_failed`, `coffees` table) distinguish "not generated yet" (worth retrying) from "Claude genuinely refused with sufficient data" (permanent — the cron backfill skips these forever, so a permanently-refusing coffee doesn't burn Claude spend on every run); an admin's `force=true` refresh ignores the flags and can always retry, resetting one on success. The backfill inherits the C2 gate for free — it calls the same `guardClaudeCall`-wrapped generation functions the old public path used, so it's bounded by the same daily ceiling/kill-switch and stops early the moment a call is blocked. Full detail: `WHAT_WE_BUILT_SECURITY.md` entry 4.
- **H1 (unbounded Anthropic bill) + M4 (content-based model escalation) closed.** New shared gate `backend/src/services/anthropicGuard.ts`: real usage-based cost (input/output tokens x per-model rate, not call count), tracked in a Postgres `claude_daily_spend` table (one row per UTC date, atomic `INSERT ... ON CONFLICT DO UPDATE` increment) so the ceiling is a true cross-instance total, not per-Cloud-Run-instance. `CLAUDE_GLOBAL_DAILY_USD` (default 20) blocks every further call once the day's spend is at/over it; `CLAUDE_ENABLED` (default true) is a separate manual kill-switch, checked first, that never even reads the spend table. Fails closed: a spend-read error blocks the call rather than allowing it. Wired into all 9 real Anthropic call sites in the app via `guardClaudeCall()` — no route/service duplicates the check. M4's content-based escalation (message word count / trigger keywords forcing Sonnet) is deleted entirely from `claude.ts`, not tuned: the authenticated Liam conversation now always uses Sonnet regardless of turn content (a single quality path, bounded by login + per-account/IP limiters + the new ceiling); every public/anon-reachable surface (quiz recommendation, coffee AI content) stays Haiku, unconditionally. Graceful, non-500 fallback at every call site when the gate blocks a call (a `sommelier is temporarily unavailable` 503 for Liam, silent fall-back-to-cached-content for coffee AI, a placeholder string for the quiz recommendation) — none write NULL over good cached content just because a call was blocked. Full detail: `WHAT_WE_BUILT_SECURITY.md` entry 3. Landed across several commits (a concurrent session's `5663151`/`38f35fc` plus this session's `3db177e`) after a shared-working-tree collision surfaced and was resolved mid-task — see that entry for the full account.
