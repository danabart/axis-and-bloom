## What this is

Brief 1 made the database describe itself. This brief makes it impossible to forget: a view that exposes the dictionary, a boot check that reports (or, in strict mode, refuses) any undescribed object, a generated `CATALOG.md` at the repo root that Dana and Claude Code read before proposing anything new, and a System Health card.

## Decisions already made (Dana). Do not re-open.

1. `CATALOG_LINT_MODE` env var: `report` (default; production today) logs findings and continues; `strict` (dev environment, when it exists) fails the boot on any finding. Read once at boot in `dataCatalogIntegrity.ts`. Brief 3 adds the one rule that fails in both modes.
2. `CATALOG.md` lives at the repo root next to `WHAT_WE_BUILT_DB.md`. It is generated, never hand-edited; the first line says so. It is committed, so Claude Code can read it without a database.

House rule, added to `CLAUDE.md` (create the file at the repo root if it does not exist): any brief that creates, alters or drops a table, view or column ends by running `npm run catalog:md` and committing the result; and before proposing any new table or view, read `CATALOG.md` and state in the brief why no existing object fits. 4. Staleness is detected, not trusted: `CATALOG.md` carries a footer with a hash of the sorted object list (names + column names + comments). The boot check computes the same hash from the live DB and reports `CATALOG.md stale` when they differ. That finding follows the lint mode like any other.

Nothing else in that file changes.

## Part A: `v_data_catalog`

One view in `schema.sql` (after the views, before the grant loops), SELECT granted to `ab_app` and `reporting_ro`:

- One row per object: `object_type` (`table`|`view`|`column`), `table_name`, `column_name` (NULL for table/view rows), `data_type`, `is_nullable`, `comment`, and the parsed comment fields `purpose`, `class`, `writer`, `readers`, `since` (split on `|`, trimmed; NULL when a field is absent), plus `is_unverified` (comment starts with `UNVERIFIED`).
- Source: `pg_class` / `pg_attribute` / `pg_description` / `pg_views`, schema `public`, no system objects, no `v_data_*` self-rows excluded (they are catalogued too).
- A second view `v_data_view_dependency` (`view_name`, `depends_on`, `depends_on_type`) from `pg_depend` / `pg_rewrite`: which tables and views each view reads.

## Part B: `dataCatalogIntegrity.ts`

Same shape as `catalogIntegrity.ts`, `runDataCatalogIntegrityChecks()` called from `index.ts` after the customer checks:

1. No table, view or table column without a comment.
2. No comment beginning `UNVERIFIED`.
3. Every table and view comment parses into the five fields with an allowed `Class`.
4. `CATALOG.md` hash matches the live hash (decision 4). Skipped with `severity: 'info'` when the file is not present on the image (Cloud Run runs from `dist/`; copy `CATALOG.md` into the image in the Dockerfile so it is present).

Each check returns the offending object names (capped at 50 in the log, full list in the System Health JSON). In `report` mode every check is `severity: 'info'`; in `strict` mode checks 1 to 4 are `severity: 'fail'` and the boot exits like the other integrity failures do today.

## Part C: `npm run catalog:md`

`tsx src/scripts/catalogMd.ts` writes `CATALOG.md`:

1. Header: generated-on timestamp, database name, counts (tables, views, columns), lint mode the generator ran with, the hash footer value.
2. Firestore block, copied verbatim from the top of `comments.sql`.
3. One section per table, grouped by `class` (master, fact, operating, snapshot, deprecated), alphabetical inside the group: the purpose line, writer, readers, since, then a column table (`column | type | null | comment`).
4. One section per view: purpose, writer/readers fields, and `reads:` from `v_data_view_dependency`.
5. A "Read before proposing a new table" paragraph at the top, quoting decision 3's rule.
6. Footer: `catalog-hash: <sha256 of the sorted object list>`.
7. Brief 3 appends two sections (lineage, activity); leave a clearly marked insertion point for them.

Deterministic output (same DB, same bytes), so a regenerate with no schema change produces no diff.
