### 1. C17 — Real per-IP rate limiting behind Cloudflare (2026-08-07)

**Context:** Closes finding M11. The Cloudflare cutover (above) put a proxy chain in front of the backend — browser → Cloudflare (proxied) → Firebase Hosting `/api/**` rewrite → Cloud Run — that `backend/src/index.ts`'s `app.set('trust proxy', 1)` (added back in #46, pre-Cloudflare, for a single-hop Cloud Run LB chain) was no longer correct for. Every `express-rate-limit` instance keys on `req.ip`; the risk was every visitor collapsing onto one shared address, silently disabling per-visitor limiting.

**Investigated empirically first, per the task's own instruction — nothing below was assumed.** Added a temporary `GET /api/_debug/ip-check` route logging `x-forwarded-for`, `cf-connecting-ip`, `req.ip`, `req.ips`, and the raw socket `remoteAddress`; deployed it (commit `9e45da1`); hit it through every real path a request can take (`axisandbloomcoffee.com`, `www.`, `axis-and-bloom-prod.web.app` direct, and the raw `*.run.app` Cloud Run origin direct, several with deliberately forged headers); read the results back from Cloud Run's logs via `gcloud logging read`. Findings:
- **X-Forwarded-For never carries the real visitor IP** in the Cloudflare→Firebase-Hosting→Cloud-Run chain. Firebase Hosting's `/api/**` rewrite *replaces* whatever X-Forwarded-For arrived with its own fresh 2-entry chain: `[whoever actually connected to Firebase Hosting, Google's own internal hop into the Cloud Run container]`. Proved this isn't spoofable at that layer by sending a forged 2-entry X-Forwarded-For straight at the `*.web.app` origin and watching it get fully discarded and replaced.
- **CF-Connecting-IP does carry the real visitor IP**, unchanged, end-to-end, on every real Cloudflare-routed request tested.
- **CF-Connecting-IP is not stripped or validated anywhere in the chain** — a request that bypasses Cloudflare (hits `*.web.app` or the raw `*.run.app` URL directly) can set an arbitrary CF-Connecting-IP and it arrives at the app untouched. Confirmed by direct test on both bypass paths. This is exactly the spoofing risk the task called out.
- **Cloud Run's own ingress (GFE) always appends the true direct TCP peer as the *last* X-Forwarded-For entry**, regardless of how many fake entries a caller prepends when hitting `*.run.app` directly. Confirmed by sending a forged leading entry and watching the real caller IP still get appended after it, un-overridable. This is what makes `trust proxy = 1` → `req.ip` a safe (if not per-visitor-specific) fallback.

**Fix:** new `backend/src/middleware/clientIp.ts`, `getRealClientIp()`. Trusts `cf-connecting-ip` as the rate-limit key **only** when X-Forwarded-For's second-to-last entry — the hop Firebase Hosting itself set from its own real TCP peer, per the finding above — falls inside Cloudflare's published IP ranges (hardcoded IPv4+IPv6 CIDR lists, sourced from `cloudflare.com/ips-v4`/`-v6`, with a manual CIDR matcher — no new dependency). Otherwise falls back to `req.ip`. `trust proxy` stays at `1`, never `true` (a blanket `true` would trust every hop and let X-Forwarded-For be spoofed freely — explicitly avoided per the task's guardrail). Wired as `keyGenerator` on every `express-rate-limit` instance in the codebase: the global limiter (`index.ts`), `sommelierIpLimiter` + `sommelierAccountLimiter`'s uid-less fallback (`routes/sommelier.ts`), `qrResolveLimiter` (`routes/qr.ts`), `funnelEventLimiter` (`routes/quiz.ts`), `redemptionLimiter` (`routes/companyGiftRedemption.ts`).

**Known residual gap, documented rather than hidden:** an attacker who skips Firebase Hosting entirely and hits the raw `*.run.app` URL can craft a single fake X-Forwarded-For entry containing a real, publicly-published Cloudflare IP address, which passes the range check and gets their forged CF-Connecting-IP trusted. Cloudflare's IP list is public, so this is "requires deliberately reading Cloudflare's docs," not accidental — but it isn't zero. **This is not closable by restricting Cloud Run ingress** — confirmed live in the GCP console 2026-08-06: the API is served via a Firebase Hosting rewrite (`/api/**` → Cloud Run in `firebase.json`), and Firebase Hosting rewrites require Cloud Run ingress = "All"; restricting it breaks the entire API, not just this bypass. The actual remediation is **C6 (Firebase App Check)**: once enforced on the backend, a direct-origin request with no valid App Check token is rejected before it ever reaches the rate limiter, so the `*.run.app` bypass — and this residual gap along with it — becomes unreachable without touching Cloud Run's ingress setting at all. C6's enforcement must exempt the `requireCronSecret` routes (`/api/cron/*`, `/api/webhooks/*`), since Cloud Scheduler and inbound webhooks legitimately call `*.run.app` directly with the cron secret, not through a browser/App-Check flow. C6 is still open (`RUN_ORDER.md` Phase 3) — not attempted in this pass. What this fix does fully close today, matching C17's acceptance bar exactly: a spoofed X-Forwarded-For **alone**, on a direct-to-origin request, never changes the keyed IP.

**Verified:** the 4 request shapes actually observed in production (real Cloudflare-routed traffic; spoofed X-Forwarded-For + spoofed CF-Connecting-IP direct to `*.run.app`; spoofed CF-Connecting-IP direct to `*.web.app` with Firebase Hosting's own X-Forwarded-For replacement; no headers at all) were replayed as unit cases against `getRealClientIp()` using the literal captured production log values — all 4 resolve correctly, including both spoof attempts correctly falling back to the real/tamper-proof IP instead of the attacker's chosen value. `tsc --noEmit` clean on the full backend both before and after removing the temp diagnostic route. Post-deploy, confirmed the diagnostic route is gone (404 direct-to-Cloud-Run) and `/health` still 200s both through Cloudflare and direct-to-Cloud-Run.

**Not done in this pass (flagged, not silently skipped):** C6 (Firebase App Check), the actual remediation for the residual gap above (`RUN_ORDER.md` Phase 3, still unchecked); IPv6 client addresses aren't grouped to a /64 subnet before keying (the installed `express-rate-limit@7.3.1` predates the `ipKeyGenerator` helper that does this upstream) — a single IPv6 visitor that rotates their low bits could get several limiter buckets instead of one; low severity, loosens the limit rather than defeating it. `M11`'s other half — "Cloudflare cannot rate-limit Firebase signup/login" — is unrelated to this fix and stays tracked separately under C6/C8 per `SECURITY_FINDINGS.md`.
