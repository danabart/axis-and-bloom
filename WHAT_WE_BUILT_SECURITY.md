### 1. C17 — Real per-IP rate limiting behind Cloudflare (2026-08-07)

**Context:** Closes finding M11. The Cloudflare cutover (above) put a proxy chain in front of the backend — browser → Cloudflare (proxied) → Firebase Hosting `/api/**` rewrite → Cloud Run — that `backend/src/index.ts`'s `app.set('trust proxy', 1)` (added back in #46, pre-Cloudflare, for a single-hop Cloud Run LB chain) was no longer correct for. Every `express-rate-limit` instance keys on `req.ip`; the risk was every visitor collapsing onto one shared address, silently disabling per-visitor limiting.

**Investigated empirically first, per the task's own instruction — nothing below was assumed.** Added a temporary `GET /api/_debug/ip-check` route logging `x-forwarded-for`, `cf-connecting-ip`, `req.ip`, `req.ips`, and the raw socket `remoteAddress`; deployed it (commit `9e45da1`); hit it through every real path a request can take (`axisandbloomcoffee.com`, `www.`, `axis-and-bloom-prod.web.app` direct, and the raw `*.run.app` Cloud Run origin direct, several with deliberately forged headers); read the results back from Cloud Run's logs via `gcloud logging read`. Findings:
- **X-Forwarded-For never carries the real visitor IP** in the Cloudflare→Firebase-Hosting→Cloud-Run chain. Firebase Hosting's `/api/**` rewrite *replaces* whatever X-Forwarded-For arrived with its own fresh 2-entry chain: `[whoever actually connected to Firebase Hosting, Google's own internal hop into the Cloud Run container]`. Proved this isn't spoofable at that layer by sending a forged 2-entry X-Forwarded-For straight at the `*.web.app` origin and watching it get fully discarded and replaced.
- **CF-Connecting-IP does carry the real visitor IP**, unchanged, end-to-end, on every real Cloudflare-routed request tested.
- **CF-Connecting-IP is not stripped or validated anywhere in the chain** — a request that bypasses Cloudflare (hits `*.web.app` or the raw `*.run.app` URL directly) can set an arbitrary CF-Connecting-IP and it arrives at the app untouched. Confirmed by direct test on both bypass paths. This is exactly the spoofing risk the task called out.
- **Cloud Run's own ingress (GFE) always appends the true direct TCP peer as the *last* X-Forwarded-For entry**, regardless of how many fake entries a caller prepends when hitting `*.run.app` directly. Confirmed by sending a forged leading entry and watching the real caller IP still get appended after it, un-overridable. This is what makes `trust proxy = 1` → `req.ip` a safe (if not per-visitor-specific) fallback.

**Fix:** new `backend/src/middleware/clientIp.ts`, `getRealClientIp()`. Trusts `cf-connecting-ip` as the rate-limit key **only** when X-Forwarded-For's second-to-last entry — the hop Firebase Hosting itself set from its own real TCP peer, per the finding above — falls inside Cloudflare's published IP ranges (hardcoded IPv4+IPv6 CIDR lists, sourced from `cloudflare.com/ips-v4`/`-v6`, with a manual CIDR matcher — no new dependency). Otherwise falls back to `req.ip`. `trust proxy` stays at `1`, never `true` (a blanket `true` would trust every hop and let X-Forwarded-For be spoofed freely — explicitly avoided per the task's guardrail). Wired as `keyGenerator` on every `express-rate-limit` instance in the codebase: the global limiter (`index.ts`), `sommelierIpLimiter` + `sommelierAccountLimiter`'s uid-less fallback (`routes/sommelier.ts`), `qrResolveLimiter` (`routes/qr.ts`), `funnelEventLimiter` (`routes/quiz.ts`), `redemptionLimiter` (`routes/companyGiftRedemption.ts`).

**Known residual gap, documented rather than hidden:** an attacker who skips Firebase Hosting entirely and hits the raw `*.run.app` URL can craft a single fake X-Forwarded-For entry containing a real, publicly-published Cloudflare IP address, which passes the range check and gets their forged CF-Connecting-IP trusted. Cloudflare's IP list is public, so this is "requires deliberately reading Cloudflare's docs," not accidental — but it isn't zero. **This is not closable by restricting Cloud Run ingress** — confirmed live in the GCP console 2026-08-06: the API is served via a Firebase Hosting rewrite (`/api/**` → Cloud Run in `firebase.json`), and Firebase Hosting rewrites require Cloud Run ingress = "All"; restricting it breaks the entire API, not just this bypass. The actual remediation is **C6 (Firebase App Check)**: once enforced on the backend, a direct-origin request with no valid App Check token is rejected before it ever reaches the rate limiter, so the `*.run.app` bypass — and this residual gap along with it — becomes unreachable without touching Cloud Run's ingress setting at all. C6's enforcement must exempt the `requireCronSecret` routes (`/api/cron/*`, `/api/webhooks/*`), since Cloud Scheduler and inbound webhooks legitimately call `*.run.app` directly with the cron secret, not through a browser/App-Check flow. C6 is still open (`RUN_ORDER.md` Phase 3) — not attempted in this pass. What this fix does fully close today, matching C17's acceptance bar exactly: a spoofed X-Forwarded-For **alone**, on a direct-to-origin request, never changes the keyed IP.

**Verified:** the 4 request shapes actually observed in production (real Cloudflare-routed traffic; spoofed X-Forwarded-For + spoofed CF-Connecting-IP direct to `*.run.app`; spoofed CF-Connecting-IP direct to `*.web.app` with Firebase Hosting's own X-Forwarded-For replacement; no headers at all) were replayed as unit cases against `getRealClientIp()` using the literal captured production log values — all 4 resolve correctly, including both spoof attempts correctly falling back to the real/tamper-proof IP instead of the attacker's chosen value. `tsc --noEmit` clean on the full backend both before and after removing the temp diagnostic route. Post-deploy, confirmed the diagnostic route is gone (404 direct-to-Cloud-Run) and `/health` still 200s direct-to-Cloud-Run. *(Correction, discovered during entry 2's testing: `/health` "200 through Cloudflare" only ever meant the custom domain's catch-all SPA rewrite serving `index.html` — `firebase.json` only rewrites `/api/**` to Cloud Run, so `/health` was never actually reachable through the public domain in the first place, same as `/health/db` below. Harmless either way — the app's real `/health` handler was, and still is, correctly live at the direct Cloud Run origin, which is what Cloud Run's own health checks use.)*

**Not done in this pass (flagged, not silently skipped):** C6 (Firebase App Check), the actual remediation for the residual gap above (`RUN_ORDER.md` Phase 3, still unchecked); IPv6 client addresses aren't grouped to a /64 subnet before keying (the installed `express-rate-limit@7.3.1` predates the `ipKeyGenerator` helper that does this upstream) — a single IPv6 visitor that rotates their low bits could get several limiter buckets instead of one; low severity, loosens the limit rather than defeating it. `M11`'s other half — "Cloudflare cannot rate-limit Firebase signup/login" — is unrelated to this fix and stays tracked separately under C6/C8 per `SECURITY_FINDINGS.md`.

**Files:** `backend/src/middleware/clientIp.ts` (new), `backend/src/index.ts`, `backend/src/routes/sommelier.ts`, `backend/src/routes/qr.ts`, `backend/src/routes/quiz.ts`, `backend/src/routes/companyGiftRedemption.ts`. Commits: `9e45da1` (temp diagnostic, since removed), `d294cc4` (the fix).

### 2. C1 — Removed the unauthenticated DB-schema-leak diagnostics (2026-08-07)

**Context:** Closes finding M1. `backend/src/index.ts` had two undocumented, unauthenticated diagnostic routes left over from early development: `GET /health/db` (queried `pg_tables` and returned every table name in the public schema) and `GET /health/session-cols` (queried `information_schema.columns` and returned `cupping_sessions`' column names/types). Neither required auth. The 2026-08-05 live scan (see the pre-existing-work summary above) had already confirmed these aren't reachable through the public custom domain — `firebase.json` only rewrites `/api/**` to Cloud Run, and `/health*` isn't under that prefix, so the public domain's catch-all rewrite serves the SPA instead — but the direct Cloud Run origin URL (`*.run.app`) was never protected, and that URL isn't secret (it's in this very repo's own docs).

**Fix:** deleted both handlers outright — no auth-gating, no feature flag, they had no legitimate use. `GET /health` (`{ status: 'ok' }`, no auth) is untouched — Cloud Run's own health checks and uptime monitoring depend on it, and it exposes nothing. No other route touched.

**Verified:** `tsc --noEmit` clean. Live, post-deploy, against the actual Cloud Run origin (the only place these routes were ever reachable): `GET /health` → 200, `GET /health/db` → 404, `GET /health/session-cols` → 404. Also reconfirmed, while verifying, that none of the three are reachable as real backend responses through the public custom domain at all — `axisandbloomcoffee.com/health` (and the two removed routes) all serve the SPA's `index.html`, not the Express app, matching the 2026-08-05 scan's M1 nuance exactly (see the correction note on entry 1 above).

**Not done in this pass:** no other C1-adjacent hardening attempted — this was a scoped two-route removal only, per the task.

**Files:** `backend/src/index.ts`. Commit: `a0fa591`.

### 3. C2 — Global Claude spend gate + removed the M4 model-tier escalation (2026-08-07)

**Context:** Closes H1 (unbounded aggregate Anthropic bill) and M4 (a customer could force the expensive Sonnet tier for free via message content — ≥20 words or a trigger word like "recommend"/"why" in `chatWithSommelier`'s matching-mode routing). Two parts, both required: a real spend ceiling that works across every Cloud Run instance, and removing the one place model choice was influenced by untrusted input.

**Part 1 — the shared gate.** New `backend/src/services/anthropicGuard.ts`, `guardClaudeCall(model, makeCall)`. Tracks **real usage-based cost**, not call count: after a successful call, reads the actual `usage.input_tokens`/`usage.output_tokens` Anthropic returns and prices it against a one-place rate table (Haiku 4.5 $1/$5 per M in/out, Sonnet 4.6 $3/$15 per M in/out), rounding each call's cost **up** to the nearest cent (under-counting spend is the failure mode to avoid). Accumulates into a new Postgres table, `claude_daily_spend` (`date DATE PRIMARY KEY, cents INT`, one row per UTC calendar date), via a single atomic `INSERT ... ON CONFLICT (date) DO UPDATE SET cents = cents + $n RETURNING cents` — a real cross-instance total, not an in-memory per-instance counter that would reset on every Cloud Run scale event. Two independent, env-driven levers: `CLAUDE_GLOBAL_DAILY_USD` (default 20) — before each call, if today's accumulated spend is at/over the ceiling, the call is rejected *before* Anthropic is ever hit; `CLAUDE_ENABLED` (default true) — a manual "stop all AI now" kill-switch, checked first, that never even reads the spend table. **Fails closed**: if the spend-read itself errors, the call is blocked, not allowed. Only a call that actually succeeds increments the total — a blocked call never reaches `makeCall()`, and a call that throws is never recorded (the increment only runs after `makeCall()` resolves).

**Part 2 — the M4 fix.** In `claude.ts`'s `chatWithSommelier`, deleted the word-count/keyword escalation logic entirely (not tuned, not gated differently) — `sonnetKeywords`/`sonnetMinMessageWords`/`useSonnet` are gone from the file. Model choice is now decided purely by surface: the authenticated Liam conversation (`chatWithSommelier` — every caller sits behind `requireAuth` + `blockAnonymousAuth`) always uses `claude-sonnet-4-6`, unconditionally, regardless of turn content, word count, or matching/expertise mode — a single quality path bounded by login + the per-account/per-IP turn limiters + `checkDailyCap` + this task's own global ceiling, not by picking a cheaper model per turn. Every public/unauthenticated or anon-reachable surface (the coffee-content endpoints, the quiz recommendation) was already hardcoded to Haiku and stays that way. Confirmed no request body, header, or query param reaches `chatWithSommelier`'s model-selection expression in any form. `config.modelRouting.expertiseModelOverride` (an existing, operator-only Firestore config slot for a manual A/B, e.g. Fable — never admin-UI-editable, confirmed) is kept as the one legitimate override, now applying to the whole authenticated conversation rather than just expertise-mode turns. The now-orphaned `sonnetKeywords`/`sonnetMinMessageWords` admin-config fields (`AdminSommelierConfig.tsx`/`AdminSommelierFlow.tsx`, `sommelierConfig.ts`, the Firestore seed) were left in place, not removed — flagged below, not silently dropped.

**Every Claude call site wired in (9 total, confirmed by grepping every `.messages.create(` in the codebase):** `claude.ts` — `chatWithSommelier` (Sonnet), `getRecommendation`, `getCoffeeSummary`, `getCoffeeSurpriseNote`, `getCoffeeThreeVoiceStory` (all Haiku); `storyLayer.ts` — `generateOnce` (full story generation) and the `attempt()` helper inside `generateOneWarmSentence` (brew-note/order-placed one-liners); `sommelierEvaluator.ts` — the Stage-2 Haiku briefing; `liamSmsFeedback.ts` — the inbound-SMS-reply parser.

**Graceful, non-500 fallback at every site — none of them just let a block become a raw 500 or silently destroy cached content:**
- `chatWithSommelier` callers (`sommelier.ts` `/start` and `/:sessionId/message`): both now catch `ClaudeGuardBlockedError` specifically. `/start` rolls back the session row it had already inserted (same rollback pattern the existing insufficient-tokens path uses) and returns `503` with a plain "Liam is temporarily unavailable" message — silently handing the customer a session with a canned opening line, that they could then send real messages into and keep failing, would have been worse than telling the truth. `/message` (previously **not** wrapped at all — a raw Anthropic error here would already have 500'd, an existing gap this task also closed) rolls back the just-saved Firestore user message and returns the same `503`. Any other/unexpected error still falls through to the pre-existing behavior unchanged.
- `getRecommendation` (`quiz.ts` `POST /results`): the quiz session is already durably saved (Cloud SQL + Firestore) by the time this call happens — a block now falls back to a plain placeholder string and still returns `200`, rather than turning an already-successful save into a `500 Failed to save quiz result`.
- `getCoffeeSummary`/`-SurpriseNote`/`-ThreeVoiceStory`/`generateCoffeeStoryWithRetry` (`coffees.ts`'s `generateAndStoreAllContent`): a new `toNullIfBlocked()` wrapper plus per-field blocked flags (`summaryBlocked`/`surpriseBlocked`/`storyVoiceBlocked`) ensure a block resolves to "nothing new, keep whatever's cached" — critically, **not** "generation ran and came back empty," which is what the pre-existing null-write logic does for a genuine refusal. Without this distinction, a kill-switch flip or hitting the ceiling would have silently overwritten every coffee's AI content with `NULL` the next time anyone requested it (worst on the admin `force: true` refresh path). The public `/ai-summary` route now returns `503` + a friendly message on a block instead of `500`.
- `storyLayer.ts`'s `generateOneWarmSentence`, `sommelierEvaluator.ts`'s briefing, `liamSmsFeedback.ts`'s reply parser: each already had its own try/catch with a sensible fallback (a generic sentence, a templated opening line, neutral-sentiment defaults) — a guard block degrades through that pre-existing path with no further changes needed.

### 4. C3 — Public coffee AI endpoints made read-only (2026-08-08)

**Context:** Closes M2. `GET /api/coffees/:id/content` and `GET /api/coffees/:id/ai-summary` — both public, unauthenticated — called Claude directly on a cache-miss. Some coffees have permanently-null content (a genuine refusal, or output that failed `looksLikeRefusal`'s check), and nothing distinguished that from "just hasn't been generated yet," so every public request for one of those ids re-generated, unbounded — an unauthenticated cost-amplification vector, bounded only by the (at the time) mis-keyed global rate limiter (C17) and, since the prior entry, the C2 daily ceiling. This closes it structurally instead: the public path can no longer reach Claude under any circumstance, full stop.

**The fix, in three parts:**

1. **Both public GET handlers are now pure reads.** The inline `generateAndStoreAllContent(id, {force:false})` / `generateAndStoreSummary(id)` calls are gone entirely — replaced with a plain `SELECT` of the cached columns. A cache-miss returns `200` with `aiSummary: ''`/`surpriseNote: null`/`threeVoiceStory: null` (or `summary: null` for the legacy `/ai-summary` route) — never a generation attempt, never a `500`. The frontend already renders this state correctly with zero changes needed: `TastingNotes.tsx`'s `'full'` variant shows "Not enough data to generate a summary yet." when `aiSummary` is falsy and conditionally omits the surprise/three-voice blocks when both are null; the `'reveal'` variant just renders nothing. Confirmed by reading the component, not assumed.

2. **Generation moved fully out-of-band, via a new daily cron job.** `GET /api/cron/coffee-content-backfill` (`requireCronSecret`, same shape as the three existing daily jobs in `cron.ts`) calls a new `backfillCoffeeContent()` (`coffees.ts`): finds every coffee still missing at least one content field (and not terminally failed — see below), and generates for each **sequentially** — not in parallel, so this doesn't burst Anthropic with N concurrent requests for what's a low-frequency nightly job, and so the C2 daily-ceiling check between each call is actually meaningful. **Chose cron over an admin-only trigger**: the existing admin `refresh-content`/`refresh-summary` endpoints (`requireAdmin`, already non-public, untouched by this task) are a real, legitimate authenticated trigger too, but they require a human to manually click per coffee — a cron job is what actually keeps the cache populated automatically as new coffees are added to the catalogue, without relying on someone remembering to trigger it. Both mechanisms now coexist: cron for automatic backfill, admin refresh for manual forced regeneration.

3. **Terminal-failure flags stop the backfill from looping on refused coffees.** Four new columns on `coffees`: `ai_summary_generation_failed`, `surprise_note_generation_failed`, `three_voice_story_generation_failed`, `story_generation_failed` (all `BOOLEAN NOT NULL DEFAULT false`). **Distinguishing "not generated yet" from "generation refused / give up":** a field is marked failed only when it was genuinely *attempted* — needed, had sufficient input data (ruled out via the existing `hasSufficientData`/`hasSufficientVoices` gates), and *not* blocked by the C2 guard — and still came back refusal-like (`looksLikeRefusal`) or, for the story field specifically, exhausted `generateCoffeeStoryWithRetry`'s retry loop without passing the specificity check. This is computed as a new `summaryRefused`/`surpriseRefused`/`storyVoiceRefused` derivation, kept deliberately separate from the pre-existing `summaryBlocked`/`surpriseBlocked`/`storyVoiceBlocked` flags from C2 (a block is "no attempt happened," never terminal; a refusal is "an attempt happened and failed," which is). `generateAndStoreAllContent`'s `needsX` checks now read these flags — `force || (!cached.field && !cached.field_generation_failed)` — so the automatic backfill (`force=false`) skips a terminally-failed field forever, while an admin's explicit `force=true` refresh ignores the flag and always retries, **resetting it to `false`** on the same UPDATE if that retry actually succeeds. A field skipped for *insufficient data* (not enough cupping/descriptor data to even try) deliberately does **not** get a terminal flag — that costs nothing to re-check each run (no Claude call happens) and should self-correct the moment real data arrives.

**The generator inherits the C2 gate for free — no new gating logic needed.** `backfillCoffeeContent()` calls the exact same `getCoffeeSummary`/`getCoffeeSurpriseNote`/`getCoffeeThreeVoiceStory`/`generateCoffeeStoryWithRetry` functions the old public path used, and every one of those is still wrapped in `guardClaudeCall()` from C2, unchanged. So the cron backfill is automatically bounded by `CLAUDE_GLOBAL_DAILY_USD`/`CLAUDE_ENABLED`, and — as an explicit belt-and-suspenders addition in this task — `backfillCoffeeContent()`'s own loop stops early the moment any call is blocked (`isClaudeGuardBlocked`), logging how many candidates were left for the next run rather than burning N more no-op round-trips through a gate that's already known to be shut.

**Confirmed neither public handler can reach Anthropic under any code path** by grepping every real call site of `generateAndStoreAllContent`/`generateAndStoreSummary`/`getCoffeeSummary`/`getCoffeeSurpriseNote`/`getCoffeeThreeVoiceStory`/`generateCoffeeStoryWithRetry` in the codebase: the only callers left are `admin.ts` (behind the router-level `requireAdmin`) and the new `backfillCoffeeContent()` (behind `requireCronSecret` via `cron.ts`) — nothing in `coffees.ts`'s two public route handlers references any of them anymore.

**Verified:** `tsc --noEmit` and `npm run build` clean. Frontend null-handling confirmed by reading `TastingNotes.tsx` directly (both variants already handle `aiSummary`/`surpriseNote`/`threeVoiceStory` all being `null`/empty without a broken state) — no frontend file touched, none needed.

**Not done in this pass, flagged not skipped:** the Cloud Scheduler job for `coffee-content-backfill` itself — the endpoint exists and is correctly gated, but nothing triggers it in production yet (same manual-setup gap the three pre-existing cron jobs have/had — see `RUN_ORDER.md` Phase 1). Until that's created, coffees with no cached content stay uncached until an admin manually hits `refresh-content`. Also not done: retroactively re-checking the 6 coffees already nulled by the earlier one-time cleanup script (WHAT_WE_BUILT.md #145) against the new terminal-flag scheme — they're currently just "missing content, flag false," so the next backfill run (once scheduled) will attempt them once more, which is the correct/desired behavior, not a gap.

**Same-day follow-up (2026-08-08), live-verification finding:** browsing the site right after this deploy turned up a second, real leaked refusal — coffee 23 ("Working Late Hours") was serving verbatim stored refusal text as its surprise-note hook, publicly. Traced (not assumed): #145's original cleanup nulled it correctly, but the code that would have stopped it recurring (`contentGuard.ts`'s guard) didn't reach a successful deploy until ~16 minutes later (the same `5663151`→`38f35fc` CI-failure gap this doc's entry 3 already describes) — in that gap the still-live old ungated `/content` route regenerated it, got a refusal again, and stored it raw. A full manual re-read of every coffee's cached content (not just the automated regex scan, which missed one — a different refusal phrasing, "I'm missing," not caught by any existing pattern) found 5 affected fields across 4 coffees total (17, 22, 23, 32). All nulled + terminal-flagged the same way C3 designed for; `contentGuard.ts`'s pattern list expanded to catch the missed phrasing. Full detail: `WHAT_WE_BUILT.md` #146.

### 5. C4 — Beats dial-in IDOR closed with a capability token (2026-08-09)

**Context:** Closes H3. `GET /api/beats/dial-in/:beatEventId/respond` identified the beat by `beat_event.id` — a plain SERIAL, unauthenticated, no ownership check. ### 8. C6a — Eliminated the App Check first-load token race in the fetch wrapper (2026-08-09)

**Context:** a same-day follow-up to entry 7, found from real production monitoring-mode logs — `GET /api/users/profile`, the first backend call of a fresh session, occasionally logged `[app-check] no token` server-side, even though the frontend wrapper already `await`ed `getToken(appCheck)` before sending. Harmless today (monitoring mode never blocks on a missing token, per entry 7's own design), but it meant a real cold-load request could still be sent unattested — and would 401 the moment `APP_CHECK_ENFORCED` ever flips to `true`, which is exactly the state entry 7's fix is building toward.

**Root cause:** `getToken(appCheck)` only resolves once App Check finishes its own async initialization (loading reCAPTCHA v3, exchanging for a first token) — a step that runs in the background after `initializeAppCheck()` returns, not before. On a cold page load, that initialization can still be in flight when the very first `/api/*` call fires (e.g. `Profile.tsx`/`AuthContext`'s own profile fetch on mount). Awaiting the real call wasn't itself wrong — the bug was that it was unbounded, meaning a slow or genuinely stuck attestation (bad network, reCAPTCHA blocked, etc.) could, in principle, turn into a hung request rather than a clean fall-open.

**Fix, scoped entirely to the wrapper in `frontend/src/app/lib/firebase.ts`:** new `getAppCheckTokenSafe()` — `Promise.race`s the real `getToken(appCheck, /* forceRefresh */ false)` call against a 2.5s (`APP_CHECK_TOKEN_TIMEOUT_MS`) timeout. Both race participants are written to *resolve*, never reject: the real call's `.catch()` resolves to `undefined` (same as before — not attested yet, offline, no live reCAPTCHA locally) and the timeout's own promise resolves to `undefined` after 2.5s. `Promise.race` naturally returns whichever side settles first — a real token if it arrives in time, `undefined` on timeout or failure — and the timer is cleared afterward either way, so no dangling handle. The outer `window.fetch` wrapper's logic is otherwise **unchanged**: `if (!token) return nativeFetch(input, init)` — the exact same fall-open path as entry 7, just now fed by a bounded wait instead of an unbounded one. No change to `isBackendApiRequest()`'s URL matching (still same-origin-or-`VITE_API_URL` + `/api/` path only), no change to `api.ts`, no second source of the header — every invariant from entry 7 holds.

**Verified:** standalone `tsc --noEmit` on the touched file, using Vite's actual resolution settings (`--moduleResolution bundler --types vite/client`, matching `vite.config.ts`) — clean. `vite build` (the project's real build gate) — clean (2142 modules, only the pre-existing unrelated font-asset warning). `git status`/`git diff` confirmed the change is scoped to exactly one file, `frontend/src/app/lib/firebase.ts` — no other file touched.

**Not done in this pass:** the 2.5s timeout value itself wasn't tuned against real network telemetry — chosen as "long enough that reCAPTCHA v3 normally finishes well inside it, short enough that a stuck attestation still fails open quickly." Revisit if real Cloud Run `[app-check]` logs, watched under entry 7's still-open "next step," show cold-load requests still frequently landing with no token even with this fix live.

### 10. C6b — Hardened anonymous sign-in to await App Check (2026-08-09)

**The fix:** `getAppCheckTokenSafe()` (C6a's own helper — `Promise.race`s a real `getToken(appCheck)` against a 2.5s timeout, both paths resolving, never rejecting, to `undefined` on failure) is now `export`ed from `firebase.ts` and reused as-is — not reimplemented — in `AuthContext.tsx`. Inside the `u === null` branch, immediately before calling `signInAnonymously(auth)`: `await getAppCheckTokenSafe();`. By the time the sign-in call actually fires, App Check has either already obtained a token (the routine case, and the whole point of this fix — the Auth SDK's interop layer then has something to attach) or the bounded wait has elapsed and sign-in proceeds unattested anyway, exactly the same fail-open contract as C6a. **Known residual gap, investigated and flagged rather than silently left implicit:** this fix only covers the *first-visit* anonymous sign-in path. A *returning* visitor with an already-persisted Firebase session (anonymous or real) never reaches the `u === null` branch at all — `getAuth(app)`'s own internal SDK logic automatically validates/refreshes that persisted session, and that internal call fires at module-load time, inside `firebase.ts` itself, before React even mounts — before this fix's `await` (which lives inside a React `useEffect`, necessarily later) gets any chance to run. `initializeAppCheck()` is called before `getAuth()` in `firebase.ts` (correct per Firebase's own guidance, already true before this task), but that only guarantees App Check's provider is *registered* first — it doesn't guarantee App Check's own async reCAPTCHA-load-and-token-exchange has *finished* by the time `getAuth()`'s internal refresh fires moments later. Closing this properly would mean deferring the app's entire Firebase Auth usage until App Check is confirmed ready — a materially bigger, riskier restructuring than this task's scope, and not what was asked. Left open, consistent with the task's own stated bar ("Auth is only in monitoring, so an occasional unverified call is fine — we just want the routine case to attest").

Kept isolated on its own branch (`security/c11-dependency-upgrades`) per the task's own instruction, given the majors involved.

**The Node-22 fork in the road, surfaced before touching any code:** `firebase-admin@14.2.0` (the version that actually fixes H5 — confirmed the entire `10.2.0–13.10.0` range, i.e. all of v13 too, is still in `npm audit`'s vulnerable range for the `@google-cloud/firestore`/`uuid` chain) declares `engines.node: >=22`, while the backend's Docker image was pinned to `node:20-alpine`. Flagged this to Dana before proceeding rather than silently picking a side — confirmed: bump the whole stack to Node 22 (not settle for v13, which wouldn't actually close H5). Two extra checks came with that decision, both done: (1) the CI runner's Node version bumped alongside the container (`actions/setup-node@v4`, both jobs, `node-version: 20` → `22`), so tests/builds run on the same major as production, not a different one; (2) Docker's own build+boot behavior on `node:22-alpine` — **not directly verifiable this session** (no Docker available in this environment) — de-risked instead by confirming the production dependency tree has **zero native/compiled modules** (the only `.node` binaries anywhere in `node_modules`, `rolldown`/`lightningcss`, are `vite`/`vitest` dev-tooling excluded from the image via `--omit=dev`, so there's no native-ABI rebuild step to fail in the first place), and covered by treating the actual CI deploy as the real boot test — watched live post-merge, with a rollback plan ready if the container failed to come up (see Verified, below — it didn't).

**Backend — `firebase-admin` 12.7.0 → 14.2.0.** A real breaking change hit immediately on `tsc --noEmit`: v13 removed the old default-export namespace (`import admin from 'firebase-admin'; admin.auth()/.firestore()/.initializeApp()/.credential.cert()/.apps/.app()`) in favor of per-service modular imports (`firebase-admin/app`, `/auth`, `/app-check`, `/firestore`). Rebuilt `services/firebase-admin.ts` entirely on the modular API (`initializeApp`/`cert`/`getApp`/`getApps` from `firebase-admin/app`, `getAuth` from `firebase-admin/auth`, `getAppCheck` from `firebase-admin/app-check`, `getFirestore`/`FieldValue` from `firebase-admin/firestore`, unchanged) — but kept the file's own default export shaped exactly like the old `admin` object (`{ auth: () => getAuth(app), appCheck: () => getAppCheck(app) }`), so every one of the 4 consumer files that actually call into it (`middleware/auth.ts`, `middleware/appCheck.ts`, `routes/auth.ts`, `services/staleGuestCleanup.ts` — confirmed by grep to be the complete list; everything else only imports `firestoreDb`/`FieldValue`) needed **zero changes**. Deliberately chose this over refactoring all 4 call sites onto the modular API directly — same functional result, far smaller/safer diff for a task that's explicitly about not breaking things.

**The remaining vulnerable package after the major bump: `uuid`, moderate, via `@google-cloud/storage`'s own older `gaxios`/`teeny-request` chain** (a dependency `firebase-admin`'s storage submodule pulls in regardless of use). `npm audit`'s own suggested `--force` fix would have **downgraded** `firebase-admin` to `10.3.0` — a known npm-audit resolver quirk on deep transitive chains, not followed. Confirmed by grep that `admin.storage()` is never called anywhere in this codebase (Firebase Storage isn't used — the image pipeline uses a separate GCS bucket directly, per `WHAT_WE_BUILT.md` #106) — this vulnerable code path is dead weight, not reachable. Patched anyway, cleanly, via `package.json`'s `overrides: { "uuid": "^11.1.1" }`, forcing the nested dependency without touching `firebase-admin`'s own version. **Backend: 15 vulnerabilities (2 low/8 moderate/4 high/1 critical) → 0.**

**Frontend — `react-router` 7.13.0 → 7.18.2, `vite` 6.3.5 → 6.4.3 (also flagged, per the task's own "and vite if flagged").** `npm audit fix` (non-forcing) alone cleared `@babel/core`, `nanoid`, `postcss`, `protobufjs`, `tar`, and `websocket-driver` (dev-only `vite`/`vitest` chain plus a stray `tar`) without any version pin changes. Remaining after that: `react-router` itself (a long list of advisories — the open-redirect L6 names, plus several others: vendored-turbo-stream RCE, stored/reflected XSS, CSRF, DoS via unbounded path expansion — all fixed together by the single 7.18.2 bump), `vite` (path-traversal/arbitrary-file-read advisories, fixed by 6.4.3), and `undici` — moderate-to-high, nested inside `firebase`'s `@firebase/auth`/`firestore`/`functions`/`storage` submodules. `undici` is a **Node-only** HTTP client with no browser build; it ships in `node_modules` because npm installs every platform variant of a package regardless of target, but Vite's browser bundling resolves `firebase`'s actual browser-target export, which uses native `fetch`, not `undici` — very likely dead code in the shipped bundle, same shape as the backend's `uuid` finding. Patched anyway via `overrides: { "undici": "^6.28.0" }` (same major, patched minor — no API surface change risk). **Frontend: 18 vulnerabilities (1 low/9 moderate/6 high/2 critical) → 0.**

**New `npm audit --omit=dev --audit-level=high` CI gate, one job each, `deploy.yml`.** Gates on **high/critical only, production dependencies only** — `--omit=dev` excludes `vite`/`vitest`'s own dev-tooling chain (the recurring `esbuild`/`postcss`/`nanoid` noise seen in both audits above, real advisories but in code that never reaches either deployed artifact — the Docker image explicitly `--omit=dev`s, and Vite bundles only from `dependencies`), so the gate can't choke on transitive dev-only findings no code change here could fix anyway; `--audit-level=high` skips low/moderate, matching this task's own stated bar. Runs **before** the Docker build/push/deploy steps (backend) and before the actual `vite build` (frontend) — a real hit blocks the job before anything reaches production, not an informational-only step. Backend's job needed a new `actions/setup-node@v4` step added (it previously had no bare Node runner step at all, only the Dockerfile's own internal `npm ci`) to have somewhere to run `npm audit` outside the container.

**Verified:** backend `tsc --noEmit` clean (after the modular-API rewrite above) and `npm run build` clean. Test suite: 15 failures, confirmed — not assumed — to be the exact pre-existing set (stashed this task's changes, reproduced the identical failure names/count against the same day's independent, unrelated `WHAT_WE_BUILT.md` #150 record: "quiz veto cascade, admin lookups, the Chocolate & Nutty `isDefault` duplicate" — matches exactly) — zero new failures, and the failure content itself (scoring-algorithm tie-break assertions, a duplicate data flag, a lookup-CRUD 404) is semantically unrelated to any package this task touched. Frontend `vite build` clean (2144 modules). **Live-exercised the actual admin-SDK surfaces this app uses, with real production credentials, not just import-level checks:** a throwaway script (deleted after use) confirmed `admin.auth().verifyIdToken()` cleanly rejects an invalid token (no crash), `admin.appCheck().createToken()` + `.verifyToken()` round-trips a real token successfully, and `firestoreDb.doc('config/sommelier').get()` — the exact document `sommelierConfig.ts` reads at every server boot — returns real data (21 keys). Both `npm audit --omit=dev --audit-level=high` gate commands confirmed passing locally (exit 0) before being added to CI.

A local `docker build`/`docker run` boot test on `node:22-alpine` wasn't performed directly (no Docker in this environment) — mitigated by the native-dependency check above and covered instead by the live CI deploy itself as the real boot test (see the merge/deploy entry this same day, once it lands).

### 12. C14 — Keyless CI via Workload Identity Federation (2026-08-10)

**Context:** closes H6 (CI authenticated to GCP with a long-lived exported service-account key, `GCP_SA_KEY`, used for both the Cloud Run and Firebase Hosting deploys — a leaked key meant non-expiring prod access across both services) and L7 (an unused `pull-requests: write` scope on the frontend job). Run as an explicitly staged rollout per the task's own instruction — stand up WIF additively, switch the workflow while keeping the old key as a fallback, prove it live, and only then rotate — never a single all-at-once cutover.

**Survey, before touching anything.** H6's own note ("OIDC is already wired") turned out to refer only to the GitHub Actions side — both jobs already declared `permissions: id-token: write`. The GCP-side Workload Identity Pool didn't exist at all (`gcloud iam workload-identity-pools list` returned `[]`, confirmed empty, not assumed). Identified the actual deploy identity, `github-actions-deploy@axis-and-bloom-prod.iam.gserviceaccount.com` ("GitHub Actions Deployer"), and confirmed it already held every role both deploys need — `run.admin`, `artifactregistry.writer`, `firebase.admin`, `iam.serviceAccountUser`, `secretmanager.secretAccessor`, `cloudsql.client`, `cloudbuild.builds.editor` — so Phase A needed no new role grants, only the WIF trust relationship itself. Found the exact exported key to eventually rotate: of 4 keys on that SA, 3 are Google `SYSTEM_MANAGED` (untouchable, not real exportable credentials) and exactly 1 is `USER_MANAGED` (`83960270d1962eb89a323324a86d13a9231e957a`, created 2026-05-21, `9999-12-31` expiry) — the actual `GCP_SA_KEY`.

**Phase A (GCP, additive — created live in the project, no code diff).** New Workload Identity Pool `github-pool` + GitHub OIDC Provider `github-provider`, issuer `https://token.actions.githubusercontent.com`. **The critical control:** the provider carries an attribute condition, `assertion.repository == 'danabart/axis-and-bloom'`, set at creation time — a GitHub OIDC token asserting any other repository is rejected by the provider itself, before it ever reaches IAM. `roles/iam.workloadIdentityUser` granted on the deploy SA, additionally scoped to `principalSet://.../attribute.repository/danabart/axis-and-bloom` rather than the whole pool — belt-and-suspenders with the provider-level condition, not redundant with it (either alone would already block other repos; both together mean a misconfiguration in one layer doesn't remove the other).

**Phase B (`deploy.yml`, `GCP_SA_KEY` left fully intact as fallback).** Both jobs' `google-github-actions/auth@v2` steps: `credentials_json: ${{ secrets.GCP_SA_KEY }}` → `workload_identity_provider` + `service_account`. Firebase Hosting was the one real design decision: `FirebaseExtended/action-hosting-deploy@v0` only accepts a `firebaseServiceAccount` key-file input, no WIF/ADC option at all — replaced entirely with a direct `npx firebase-tools@latest deploy --only hosting --project axis-and-bloom-prod --non-interactive` step, run in the same job right after `auth`, riding the `GOOGLE_APPLICATION_CREDENTIALS` WIF-derived credential file `google-github-actions/auth@v2` exports for later steps automatically — no separate `firebase login`, no key anywhere in that path. `firebase.json` lives at repo root (`hosting.public: "frontend/dist"`), so the step's default working directory (repo root) resolves it exactly like the old action did; `firebase deploy --only hosting` targets the live channel by default, matching the old `channelId: live`. L7: removed the frontend job's `pull-requests: write` — this workflow only triggers on `push: branches: [main]`, never a PR context, confirmed by re-reading the trigger block, so the scope had nothing to ever act on.

**Phase C — pushed, watched, proven live, then stopped and reported before touching the key, exactly as instructed.** Real deploy, both jobs `success`, every step `success` (`gh`-API-equivalent job/step breakdown pulled directly from the GitHub Actions REST API, not inferred from the UI). Three things proven, none assumed:
1. **WIF, not the key, actually authenticated.** The workflow file contains zero references to `GCP_SA_KEY` after Phase B, so a successful auth step already implies WIF by elimination — but confirmed directly anyway, via Cloud Audit Logs: three `GenerateAccessToken`/`iam.serviceAccounts.getAccessToken` events on `iamcredentials.googleapis.com`, timestamped exactly inside the run's window, from GitHub Actions runner IPs (Azure-hosted, matching `client-os-ver 6.17.0-1020-azure`), `lifetime: "3600s"` short-lived tokens, one explicitly carrying `environment/github-actions-setup-gcloud` in its user agent. 3. **Firebase Hosting deploy succeeded via the new CLI path.** `Deploy to Firebase Hosting` step: success; live site `200`. Confirmed afterward: the deploy SA's key list now shows only the 3 untouched `SYSTEM_MANAGED` keys — **zero exportable long-lived credentials remain on this service account.** Production re-confirmed healthy (`/health` → `200`) after the key was gone, closing the loop.

### 13. C12 — Security headers on the static site (report-only CSP) + CORS hardening (2026-08-11)

**Context:** closes L5 outright; partially addresses M5 (the static site had zero security response headers — Helmet only wraps `/api`, Firebase Hosting sent only `Cache-Control`). Fully closing M5 means an *enforcing* CSP; this task deliberately stops at report-only, per its own explicit safety instruction — App Check enforcement is live on the backend (entry 9), and a wrong enforcing CSP that blocked Google reCAPTCHA would stop App Check from minting tokens at all, 401ing the entire API for every real visitor. Report-only first, reviewed, enforced later as a separate decision.

**Step 1 — live-audited both origins before touching anything**, `curl -sI` on `axisandbloomcoffee.com` (custom domain, via Cloudflare) and `axis-and-bloom-prod.web.app` (direct Hosting, bypasses Cloudflare). Custom domain already had `X-Frame-Options: DENY`, `strict-transport-security`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff` — all from Cloudflare's edge (per the earlier Cloudflare cutover work), no CSP, no Permissions-Policy. Direct Hosting origin had **only** HSTS (Firebase Hosting's own platform default, not anything in this repo's `firebase.json`) — confirms M5's core finding exactly: the direct-origin path was wide open.

**Step 2 — reconciled against the edge instead of duplicating blindly.** New site-wide `firebase.json` headers block (`source: "**"`, layered alongside the existing `/index.html`/`**/*.@(js|css|woff2)` Cache-Control blocks — Firebase Hosting merges header blocks that match the same request). Added `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` — values matched to what Cloudflare already sends where it already sends them, closing the direct-Hosting-origin gap without creating a second/conflicting value on the custom domain. `Permissions-Policy` (`camera=(), microphone=(), geolocation=(), payment=(), usb=(), interest-cohort=()`) was new at both layers. **One Cloudflare-side flag, not a code fix:** the edge's own HSTS value (`max-age=31556926`, no `includeSubDomains`/`preload`) is weaker than the stronger value now set in `firebase.json` — if the Cloudflare Transform Rule uses overwrite semantics it could keep the weaker value live on the custom domain. Live-verified after deploy that this concern didn't actually materialize — the custom domain now correctly shows the **stronger** `includeSubDomains; preload` value, meaning Cloudflare isn't overwriting it — still worth a Cloudflare-side cleanup to make that not rely on incidental pass-through behavior.

**Step 3 — the CSP, built from an actual code survey, not guessed.** A sub-agent grepped the entire frontend source plus the installed Firebase SDK source for every real external origin the app loads from or connects to, rather than assuming. One correction came out of it: App Check's real token-exchange endpoint is `content-firebaseappcheck.googleapis.com`, not the plain `firebaseappcheck.googleapis.com` this doc's earlier entries had assumed. Full policy, deployed as `Content-Security-Policy-Report-Only`:
```
default-src 'self';
script-src 'self' https://www.google.com https://www.gstatic.com https://www.googletagmanager.com https://connect.facebook.net;
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
font-src 'self' https://fonts.gstatic.com;
img-src 'self' data: https://storage.googleapis.com https://www.gstatic.com https://www.google.com https://www.facebook.com https://i.imgur.com https://images.unsplash.com;
media-src 'self' https://storage.googleapis.com;
connect-src 'self' https://content-firebaseappcheck.googleapis.com https://identitytoolkit.googleapis.com https://securetoken.googleapis.com https://firestore.googleapis.com https://www.google.com https://www.gstatic.com https://www.google-analytics.com https://analytics.google.com https://www.facebook.com;
frame-src https://www.google.com;
object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```
`style-src 'unsafe-inline'` is a deliberate, necessary trade-off — the app uses inline `style={{...}}` extensively (Tailwind/React pattern), removing it all is out of scope. `script-src` has no `'unsafe-inline'` — no inline `<script>` blocks exist anywhere in the built app (confirmed: `index.html` has one `type="module"` tag only; GA4/Meta Pixel are loaded via `document.createElement('script')` setting `.src` to an external URL, not inline code, so they're `script-src` origin-allowlist concerns, not inline-script ones). `fonts.googleapis.com`/`fonts.gstatic.com` cover the static `public/match/*/index.html` pages (outside the SPA proper but same-origin production pages under this same domain/CSP) that link Google Fonts directly. Two side-findings from the survey, flagged not fixed: `frontend/src/design/FONT/Lato/Lato-Regular.ttf` is referenced by `fonts.css` but doesn't exist in the repo (pre-existing broken font reference, unrelated to CSP); `SignIn.tsx`/`JoinHousehold.tsx` hardcode `i.imgur.com`/`images.unsplash.com` placeholder background images (real, included in `img-src`, worth self-hosting later). No `report-uri`/`report-to` configured — deliberately verified via direct browser inspection instead of building a report-collection endpoint (see Verified, below).

**Step 4 — CORS (L5).** `backend/src/index.ts`: prod domains (`www.axisandbloomcoffee.com`, `axisandbloomcoffee.com`, both Firebase Hosting origins) hardcoded in a `prodOrigins` array, no longer solely dependent on `FRONTEND_URL`. The `localhost:5173` dev fallback only appears when `process.env.NODE_ENV !== 'production'` — the Dockerfile sets `NODE_ENV=production` in its runner stage, so production can never see it regardless of whether `FRONTEND_URL` is set.

**Step 5 — live verification, real browser, real backend logs, not assumed clean.**
- `curl -sI` re-run on both origins post-deploy: `Content-Security-Policy-Report-Only` present with the exact policy text on both; all five other headers present and matching, no duplicates, no conflicts.

A `securitypolicyviolation` event listener was used instead of relying on the extension's own console-message capture, which turned out not to surface native CSP violation events (verified with a synthetic `console.warn` marker first, to confirm the capture pipeline actually worked before trusting an empty result from it) — **zero violations** across the entire browse.
